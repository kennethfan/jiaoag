# jiaoag v1 实施计划

单用户编码 agent：`jiaoag-server` 持有会话/任务/工具执行，`jiaoag-tui` 只做渲染与审批，两者通过 WebSocket 长连接通信。v1 的完成定义是：**在指定仓库里说「给 X 函数加测试」→ 读文件 → 流式输出 → 出 diff → 批准落盘 → 跑 `go test` → 回显结果**。

决策依据见 `CONTEXT.md`、`docs/design/agent-architecture.md` 与 `docs/adr/0001..0012`。

---

## 1. 目录与依赖方向

```
jiaoag/                          module github.com/kennethfan/jiaoag
├── cmd/
│   ├── jiaoag-server/main.go    # 装配：config → store → app → server
│   └── jiaoag-tui/main.go       # 装配：config → tui
├── internal/
│   ├── protocol/     # 线上契约：信封、帧、错误码（只依赖标准库）
│   ├── config/       # ~/.config/jiaoag/config.yaml，key 解析（$ENV / file:）
│   ├── domain/       # 类型 + 状态机 + Transition/Decision/ApprovalSource（只依赖标准库）
│   ├── limits/       # 跨层硬上限的唯一出处（MaxPayloadBytes = 256 KB）
│   ├── patch/        # 纯计算：sha256、换行归一、unified diff
│   ├── event/        # Journal 接口 + Hub（订阅/回放/seq 契约）
│   ├── store/        # SQLite：7 张表、投影更新、审计（实现 Journal）
│   ├── workspace/    # 工作区根、路径边界、读取、快照/摘要、原子写（拒绝二进制/.git/符号链接）
│   ├── exec/         # 执行后端（ADR-0011）：进程组、超时/取消杀组、输出收敛与落文件
│   ├── tools/        # 工具契约（Prepare/Execute）+ read/grep/glob/write/edit + run/check_command + read_output + git 只读
│   ├── perm/         # 权限策略纯函数：副作用分级 + 规则集 / 参数级 argv 白名单（ADR-0004）
│   ├── llm/          # Provider 端口 + openai 兼容 + anthropic 适配器 + 装饰器
│   ├── prompt/       # 提示词分层装配、{{var}} 替换、扩展指纹 hash
│   ├── agent/        # 轮次循环、上下文装配、审批挂起/恢复（只经 Recorder 落库）
│   ├── app/          # 用例编排：命令边界、事务、seq 分配、事件广播
│   ├── server/       # WS 入口、鉴权、连接/订阅桥接（无业务逻辑）
│   ├── tui/          # bubbletea：会话列表 / 对话 / 审批弹层
│   └── version/      # 版本号（hello 帧与构建注入）
└── docs/{adr,design,plans,agents}
```

依赖只允许单向（逐包清单见 `docs/design/agent-architecture.md` §3）：`cmd → app|server|tui`；`app → agent|store|event|llm|tools|workspace|exec`；`agent → llm|tools|perm|prompt|patch|workspace`；`tools → exec|patch|workspace|limits`；`perm → tools`；`workspace → patch`；`patch → limits`；`event|store → domain`。硬规则：`agent` 不得 import `store`/`server`/`tui`（落库经 `Recorder` 接口）；`server` 不得 import `store`/`agent`/`tools`（只经 `app`）；`tools` 不得 import `perm`（工具只声明副作用，不决定是否审批）；`domain`/`protocol` 只依赖标准库。

### 1.1 供应商配置（`providers[]`）

| 字段 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `name` | 是 | — | 唯一标识，用于日志与会话绑定 |
| `type` | 是 | — | `openai`（兼容协议）或 `anthropic`（Messages API） |
| `base_url` | 是 | — | 不含端点路径：`openai` 拼 `/chat/completions`，`anthropic` 拼 `/v1/messages` |
| `model` | 是 | — | 默认模型，可被单次请求覆盖 |
| `api_key` | 是 | — | 明文 / `$ENV_NAME` / `file:/abs/path`，构造时解析一次 |
| `timeout_seconds` | 否 | 120 | 单次尝试的首块超时；流式收到首块后改用空闲超时（一半，下限 5 秒） |
| `max_retries` | 否 | 2 | 只对限流（429）、请求超时/过早（408/425）与暂时性失败（5xx / 网络）生效，不含第一次调用；显式 `0` 表示不重试 |

装饰器顺序固定为 `retry(timeout(adapter))`：每次尝试独立计时，重试等待不计入超时。流式一旦向调用方推送过任何增量就不再重试，避免重复渲染；流式读取阶段的网络错误按暂时性失败重试，单行超过 4 MB 属于协议体量问题，不重试。

工具结果为空（例如静默成功的命令）时，两家仍会显式发送 `content: ""`——`content` 是必填字段，省略会让下一轮请求被拒。Anthropic 的 `tool_result` 会排在同一条消息的文本之前，多条结果按工具调用顺序排列。

## 2. 领域状态机

**任务 Task**：`queued → running ⇄ waiting_approval → completed | failed | canceled`

- `waiting_approval` 由工具调用阻塞触发，审批结果沿事件流回传后回到 `running`。
- 取消：`ctx` 取消贯穿 provider 调用与命令执行；已落盘的文件不回滚（回滚靠 git）。
- 任务生命期与连接解耦：连接断开不改变任务状态。
- 会话内并发：同一会话最多一个 `running` 任务，其余 `queued` 排队（上下文不交错，事件单写者）；跨会话不限并发。

**工具调用 ToolCall**：`requested → prepared → (waiting_approval → approved | denied | canceled) | running → succeeded | failed | canceled`。写入与命令在 `waiting_approval` 上阻塞；`denied` / `canceled` 是终态，不会被后续的 `tool.result` 覆盖成 `failed`——「用户拒绝」「任务取消」和「工具出错」在审计里是三件事。每个 `tool_use` 恰好一条 `tool.result`，等不到裁决就结束的调用补 `canceled`。

## 3. 线上协议（WS，JSON）

信封：`{v: 1, id, type, payload}`；服务端事件额外带 `{session_id, seq}`，`seq` 为会话内单调递增 int64。

**C→S**：`session.create{workspace, provider, model}`、`session.list`、`task.submit{session_id, text}`、`task.cancel{session_id, task_id}`、`event.subscribe{session_id, from_seq}`、`approval.resolve{session_id, approval_id, decision: allow_once|allow_session|deny, note}`

**S→C**：`hello{server_version, protocol_version}`、`session.created`、`session.list.result`、`task.queued`、`event{kind, task_id, payload}`（信封带 `session_id`/`seq`/`ts`）、`error{code, message}`

**事件类型（v1）**：`session.created{workspace, provider, model, title}`、`task.queued{prompt}`、`task.status{from, to, reason, error}`（所有任务状态迁移统一走这一种）、`round.started`、`assistant.start`、`assistant.message`、`tool.requested`、`tool.prepared{side_effect, paths}`、`approval.requested{approval_id, kind, risk, path, diff, truncated|command}`（diff 只挂在这里；`truncated` 表示 diff 已被 256 KB 上限截断，客户端必须据此提示「没看全」）、`approval.resolved{decision, source, note}`、`proposal.created{proposal_id, path, base_hash}`、`proposal.applied{proposal_id, path, new_hash}`、`proposal.rejected{proposal_id, path, status, reason}`（`status` 取 `rejected|stale|failed`：三种「没落盘」结局对回放是同一个含义）、`tool.result{status, exit_code, output, truncated, output_path, duration_ms}`、`error{code, message, retryable}`

**回放语义**：重连一律 `event.subscribe{from_seq: 0}` 全量重放，并在收到重放事件前清空本地视图；增量回放（`from_seq: last+1`）与「待审批快照」留到 v2——`approval.requested` 可能发生在已见 `seq` 之前，增量会让待审批面板永久不出现。服务端顺序必须是「先订阅进缓冲 → 回放 → 刷缓冲按 seq 去重」，反序会漏事件。客户端所有状态必须可从事件流重建，因此用户提问也由 `task.queued{prompt}` 渲染，而不是客户端本地回显。

流式 `assistant.delta` **不落库**：只持久化 `assistant.start` 与 `assistant.message`，delta 带 seq 但不进 `events` 表，因此 `seq` 允许空洞——客户端只要求不重复、不乱序（见 ADR-0005）。

## 4. 数据表（SQLite，WAL，`busy_timeout=5000`）

| 表 | 关键列 |
|---|---|
| `sessions` | id TEXT PK, workspace, provider, model, title, created_at, updated_at |
| `tasks` | id PK, session_id, status, prompt, system_prompt_hash, extensions_digest, **last_seq**, created_at, started_at, finished_at, error, prompt_tokens, completion_tokens |
| `events` | session_id, seq, **v**, type, payload JSON, created_at, **task_id**，PK(session_id, seq) |
| `tool_calls` | id PK, task_id, session_id, round, name, args JSON, status, approval_id, output_path, exit_code, error, created_at, ended_at |
| `approvals` | id PK, tool_call_id, kind, risk, decision, source(user/policy/system), requested_at, resolved_at, note |
| `proposals` | id PK, task_id, path, diff, base_hash, new_hash, status(pending/applied/rejected/stale/failed), applied_at |
| `audit` | id INTEGER PK AUTOINCREMENT, ts, actor, action, tool_call_id, detail JSON（只追加，不更新） |

写入串行化：单写者（一个 goroutine 或 `BEGIN IMMEDIATE`），其余读走 WAL 快照。事件追加与 `tool_calls` 状态变更在同一事务内，避免「事件有、记录无」。

迁移只增不改：已提交的 `000N_*.sql` 不可原地修改，结构变更一律新增迁移文件。`schema_migrations` 记录每个迁移的 sha256 校验和，启动时比对；内容与记录不符会拒绝启动（否则旧库版本号不变、迁移被跳过，新列直接以 `no such column` 暴露）。`migrate` 末尾还会探测 `events`/`tasks` 的热路径列作为二次兜底。

`extensions_digest` = hash(工具集版本 + 规则集 `Hash` + `ExecBackend` 名 + `system_prompt_hash`)，回答「这一轮由哪套扩展组合跑出来」，不必 join 审计表。

## 5. 权限策略（`internal/perm`）

第 3 层的取舍见 `docs/adr/0004-default-deny-command-whitelist.md`。

规则集是不可变快照 `Ruleset{Version, Hash, Rules}`（内嵌默认 + `~/.config/jiaoag/policy.d/*.yaml`），重新加载时原子替换；每次判定把 `PolicyVersion` 写进审计。外部规则只能收紧（`TightenRule` 只能返回需审批 / 拒绝），放宽必须改本地配置，见 `docs/adr/0010-policy-data-not-policy-logic.md`。

按顺序判定，短路返回：

1. **路径边界**：`filepath.EvalSymlinks` 后必须落在 workspace 根之内，否则 `deny(path_outside_workspace)`。
2. **工具分级**：只读工具（read/grep/glob、`read_output`、git 的 `git_status` / `git_diff` / `git_log` 专用工具）→ 自动放行；写入工具 → 必审批（生成变更提案）；`run_command` / `check_command` → 见 3。
3. **命令白名单（默认拒绝）**：仅当命令 argv **不含任何 shell 元字符**（`| & ; < > $ \` ( ) * ? [ ] ~`）、`argv[0]` 是**程序名本身**（带路径分隔符一律审批），且首 token 命中白名单（`go test|vet|run`、`ls`、`cat`、`head`、`wc`）时自动放行；白名单还约束参数：flag 必须在 `allow_flags` 内（`--output`、`-exec` 等一律审批），非 flag 参数必须落在工作区根内；`check_command` 的失败诊断只取尾部 2 KB。其余一律需审批。**不做「危险命令黑名单」**——字符串检测无法防住命令替换与编码执行。`go build` 与 git 子命令不在白名单：前者会把产物写进工作区（等于免审批落盘），后者会执行仓库配置里的外部程序（见 5.3 的 git 加固）。
4. **执行约束**：`cwd` 强制为 workspace 根；`env` 剥离密钥类变量（`*KEY*`、`*TOKEN*`、`*SECRET*`）；单命令超时默认 120s；事件输出 8 KB（头 6 + 尾 2，`check_command` 只取尾部 2 KB），全文落 `~/.local/share/jiaoag/outputs/`（4 MB 上限）。执行位置由 `ExecBackend` 决定（v1 只有 `direct`，v2 可接 sandbox；工具无权指定），后端身份与最终 argv 入审计，见 `docs/adr/0011-pluggable-exec-backends.md`。
5. **落盘 CAS**：`write/edit` 批准时记录目标文件 sha256；落盘前重算，不等则拒绝并要求重新出 diff（`stale_proposal`）。
6. **审批来源**：`policy`（自动放行：命令白名单，或 `allow_session` 命中会话白名单）、`user`（`allow_once` / `allow_session`，后者仅对同一 tool+args hash 生效）或 `system`（进程重启清理遗留审批、任务取消收尾，结局是 `expired`）。全部写入 `audit`。

### 5.1 任务执行与临时帧（M3）

- 一个会话同时只跑一个任务：已有 running 时新任务落库为 `queued` 并进会话内 FIFO 内存队列，当前任务收尾后自动拉起队首（M6）。排队不落第二份状态，仍以事件日志为准。`session_busy` 不再产生（协议常量保留，供旧客户端兼容）。
- `task.cancel{session_id,task_id}`：排队中的任务先从内存队列摘除再转 `canceled`（不会被误拉起）；运行中的任务由 agent 观察 ctx 自行收尾并记录终态；已终止的任务是幂等的空操作。
- 会话内串行、跨会话并行：任务协程各自独立，`recover` 兜住边界外 panic（用户已取消时记 `canceled`，否则 `failed{internal_error}`），堆栈只进服务端日志；写终态前先把该任务未完成的 tool_call / 提案收尾，避免留下没有 `tool.result` 的 `tool_use`。
- 同仓只警告不拒绝：创建会话时若同 workspace 还有未终态任务的会话，`session.created.shared_workspace` 列出对方 id（路径按 `Clean` + `EvalSymlinks` 归一）；写入仍有 CAS 保护，命令与构建可能互踩。
- `assistant.delta` 以 **seq=0 的临时帧**扇出：不占 seq、不落库、不进回放。客户端按到达顺序渲染，收到 `assistant.message` 后以完整文本为准。
- 上下文预算 `agent.context_budget_chars`（默认 60000，UTF-8 字符数）：单条工具结果超 8 KB 折成首 4 KB + 尾 2 KB；总字符超预算从最旧一轮整轮丢弃；system 与最后一条 user 消息永不丢。
- `ErrContextOverflow` 收缩预算一次后重试；再次超限记 `context_overflow` 失败。鉴权/请求错误不重试，直接记 `provider_error`。

### 5.2 写入与审批（M4）

- 工具仍是两段式：`Prepare` 只算不写（读快照、算新旧 sha256、生成 unified diff），**写入工具的 `Execute` 失败关闭**——直接调用只会得到「必须经过审批」的错误。落盘唯一路径是 `agent → workspace.Write`（临时文件 + `rename`，保留原权限）。
- 审批三段流：`proposal.created` + `approval.requested`（含 diff）一次原子迁移落库 → 阻塞等裁决（`AwaitApproval`）→ 批准后做 CAS 再落盘，记 `approval.resolved` + `proposal.applied`；拒绝、失效、写失败统一记 `approval.resolved` + `proposal.rejected{status}`。
- CAS：批准后重算目标文件 sha256 与提案的 `base_hash` 比对；不等说明审阅期间文件被改过，此时不覆盖，提案转 `stale`，工具结果返回 `stale_proposal` 让模型重新读、重新出 diff。
- 审批不设超时，只有任务取消能打断。取消时审批用 `context.WithoutCancel` 收尾成 `expired`（`source=system`）、提案转 `stale` 并记一条 `proposal.rejected`、工具调用标 `canceled`——不能留下永远等不到裁决的 `pending`，也不能让事件日志里留一条永远 `pending` 的提案或停在 `waiting_approval` 的调用。
- `allow_session` 只在内存里按会话生效，键是 `sha256(tool + "\x00" + args 原文)`；命中即放行，但仍记 `approval.resolved{source: policy}`——放行也是一次决定，审计不能缺。v1 没有「会话结束」事件，因此它实际等于「进程内有效」：进程退出即清空，不落盘、不跨连接继承。
- 换行风格保留：diff 与匹配一律先归一到 LF，写盘时按原文件的 LF/CRLF 还原，避免「只改一行」变成「整篇重写」。含 NUL 的二进制、越界路径、`.git` 内部、父目录不存在、目标本身是符号链接一律拒绝（写入用 `rename` 替换的是链接，跟用户批准的那份 diff 不是同一件事）。
- 行级 diff 表达不了的改动在 `Prepare` 阶段就拒绝：新建空文件、以及只差结尾换行（`patch.Unified` 对这两者都产出空串）。用户看不见的改动不能进审批——面板上没有内容就等于盲批。
- 进程启动时 `ExpirePendingApprovals` 清理上一次留下的待审批（标 `expired`、提案标 `stale` 并记 `proposal.rejected`、工具调用标 `canceled`、无协程的任务标 `canceled`）：v1 不自动续跑，留着它们只会让会话看起来永远卡在「等你批准」。
- 紧接着 `ReapUnfinished` 收尾没有审批行可查的遗留状态：停在 `requested|prepared|waiting_approval|running` 且没有 `tool.result` 的调用标 `canceled` 并补一条结果（审批已裁决的那批写「执行中进程重启，结果未知」——它们大概率已经开始执行，但结果无从判断），仍未终止的任务标 `canceled`；`CheckApprovalConsistency` 留作安全网，正常情况下应为空。
- `tool.result.duration_ms` 只算工具本身的时间：写入路径在审批返回后重新起算，人工审阅的等待不计入（否则离开十分钟再批准会写进一个 `600000 ms`）。
- TUI 审批面板占用输入区：`y` 批准一次、`a` 本会话内都批准、`n` 拒绝，`↑↓`/`pgup`/`pgdn` 翻 diff，面板头显示 `+N −M`（diff 被截断时标注）；`esc` 在面板里不退出（防误按），`ctrl+r` 重连带新会话，退出只认 `ctrl+c`。

### 5.3 执行与审计（M5）

- 命令生命周期：`Prepare` 校验 argv 形状（空 argv、NUL、单 token > 4 KB、token 数 > 128 一律降级成工具错误）→ cwd 固定为 workspace 根 → env 白名单剥离（含 `KEY` / `TOKEN` / `SECRET` / `PASSWORD` / `CREDENTIAL` 的变量丢弃）→ `perm.Evaluate` 判定（元字符 → 参数级白名单 → 默认审批）→ 裁决后经 `ExecBackend` 执行。工具永不启动 shell，只收 `argv[]`。
- 两个命令工具共用同一套 Prepare / 审批 / 审计，只差结果收敛：`run_command` 带回头 6 KB + 尾 2 KB 的合并输出（正文预留约 200 字节给「退出码 N」与日志警告，保证连同前缀仍在 agent 的 8 KB 二次截断阈值内）；`check_command` 成功只回「退出码 0」，失败回尾部诊断 2 KB；诊断取合并流的末尾，不做 stderr 优先——`go build` 的错误多在 stderr、`go test` 的失败细节在 stdout，按流挑选会丢掉另一类最有用的一段。全文流式写 `<output_dir>/<session>/<task>/<tool_call>.log`（4 MB 上限，写满后继续 drain 不阻塞子进程），`tool.result` 带 `output_path` 与 `truncated`。
- 模型不必重跑命令：`read_output{tool_call_id, offset?, limit?}` 按行补看中段（默认 500 行、上限 2000 行 / 256 KB）。路径不来自模型：由 `tool_calls.output_path` 反查，并校验落在本会话的输出子树内。日志写失败时 `output_path` 会被收回（不给模型一个读不全的文件）。
- `git_status` / `git_diff` / `git_log` 内部拼固定 argv（模型只填受约束的 path / ref / 行数），不透传 flag——`git -c core.pager='sh -c ...' log` 就是一条绕过审批的任意执行通道。三项工具还固定注入 `GIT_CONFIG_K=V core.fsmonitor=false` 与 `--no-ext-diff --no-textconv`：仓库配置里的 fsmonitor / diff.external / gitattributes driver 都是「只读」名义下的外部命令执行点。事件保留 8 KB（与命令工具一致），全文同样落 `<output_dir>`，可被 `read_output` 补看。
- 命令进入执行前会显式投影成 `running`：审批等待与真正执行是两件事，投影一直停在 `waiting_approval` 会让界面与崩溃排查都读错。
- 超时与取消都杀整个进程组（`Setpgid`），不留孤儿；任务照常进入明确终态。
- 审计：命令类工具每次执行恰写一条，与 `tool.result` 同事务。动作 `exec.allow`（白名单 / git 只读）、`exec.approved`、`exec.denied`、`exec.timeout`、`exec.failed`、`tool.denied`（写入或策略拒绝）；`actor` 取 `policy` / `user` / `system`。`detail` 含 `argv`、`cwd`、`backend`、`backend_version`、`policy_version`、`rule_id`、`exit_code`、`output_path`、`log_error`、`duration_ms`。
- `extensions_digest` 纳入 `ruleset.Hash` 与后端名：这一轮由哪套规则、哪个后端跑出来，不 join 审计也能回答。

## 7. 依赖与开放问题

- WS 已定 `github.com/coder/websocket`（M0 落地），SQLite 用 `modernc.org/sqlite`（纯 Go，免 cgo），diff 用 `github.com/pmezard/go-difflib`，配置用 `gopkg.in/yaml.v3`，TUI 用 `charm.land/bubbletea/v2`。
- 已定分叉（见架构文档 §11）：会话内任务排队；流式 delta 不入库、seq 允许空洞；上下文预算按 UTF-8 字符数；审批不设超时。
- **不设并发上限**是已接受的决策：M6 只展示每个会话的运行态，不拦截资源；若之后出现机器被 `npm i` 打满，再补配额。
- **v2 再谈**：上下文压缩、MCP、websearch、并行工具调用、多 provider 之外的第三家、远程部署的传输加密、插件宿主、签名安全 feed、隔离执行后端。
- 扩展缝在 v1 只留接口不加运行时（见架构文档 §12、`docs/adr/0009-extension-boundaries.md`）：`tools.Source`、`agent.Compactor`、`perm.Loader` / `TightenRule`、`ExecBackend`（仅 `direct` 实现）、`prompt.Assemble`（分层装配 + 项目级确认）。
- 命令白名单的具体条目要在 M5 用真实使用数据校准一次，否则会过窄（烦）或过宽（危险）。
