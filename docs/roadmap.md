# 路线图与剩余工作

这份文件回答一个问题：**现在还能做什么**。已经做完的东西不再逐条列出，见 `README.md` 的进度表（v1.0–v2.58）与 `docs/adr/` 的决策记录。

## 判断标准

一个候选值不值得做，看三条：

1. **有真实痛点**，不是「架构上应该有」。
2. **不改核心不变量**——事件日志语义、状态机与审批流、权限引擎只能收紧，这三样不动。
3. **单机单用户前提下成立**，需要中心化服务或多人协作的先不做。

按这三条，供应商注册表与远程执行后端已明确关闭（收益低于维护成本），见下文「明确不做」。

## 明确不做

记录下来是为了避免反复讨论：

- **LLM 供应商注册表**（C2）：单用户两三个 provider，配置里的列表已经够用，注册表只增加一层间接。
- **远程执行后端**（SSH / 容器）：单机是主场景，收益低；需要时用 `exec.backend: sandbox` 已能限住写入范围。
- **并行工具调用**：与「逐个审批 + 串行审计」强耦合，收益不抵复杂度。
- **细于 hunk 的行级勾选**：hunk 是语义上能说清的最小单位，行级会让审批变成噪音。
- **执行中任务续跑**：重启只恢复 `queued`，执行中的任务一律 `canceled`。副作用无法安全重放。
- **事件日志语义、状态机、审批流程可插拔**：这是三条不变量，不开放。
- **向量检索 / 语义记忆**：`MEMORY.md` 够用，检索层引入 embedding 依赖与不确定召回。
- **TUI golden 快照**：`internal/tui/layout_test.go` 已经锁住帧高、末三行、关键文案与溢出裁剪；再叠一层全帧基准，任何提示语微调都会让一批基准全红，维护成本和收益不成比例。

## 怎么开始一项新工作

1. 有 issue 的先看 issue；没有就先写成 issue（模板见 `docs/agents/issue-tracker.md`），把验收标准写清楚。
2. 改动前确认它不碰三条不变量；碰了就说明理由并记 ADR。
3. 实现完跑 `make check`，需要肉眼验收的（TUI、通知、真实 provider）单独验一遍。
4. 文档同步：`README.md` 进度表加一行、`docs/design/architecture-v3.md` 对应小节更新、必要时补 ADR 与专题文档。
