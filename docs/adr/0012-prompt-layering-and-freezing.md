# 提示词分层，核心段不可覆盖

「允许用户定义提示词」听起来是一个开关，实际上涉及五类完全不同的东西，价值与风险差一个量级：

| 类别 | 定制价值 | 定制风险 |
|---|---|---|
| 系统提示（角色 / 工作方式） | 高：项目约定、团队规范 | 中：写坏了模型变笨，且没有报错 |
| 工具描述 `Spec.Description` | 中 | **高**：篡改描述能让模型误用工具，比如把写盘说成只读 |
| 压缩 / 摘要提示 | 低 | 中：影响上下文完整性，坏得很隐蔽 |
| 审批话术（拒绝理由回灌） | 低 | 中：可能诱导模型绕过审批 |
| 项目知识（构建命令、禁区） | **最高** | 高：来自仓库，等于让别人的代码对你下指令 |

一刀切地「全部开放」会把第 2、4 类变成攻击面，而「全部锁死」又等于把最有价值的一类（项目知识）拒之门外。因此按类分治，并且把用户可写的那部分放在核心协议之上，而不是替代它。

## 分层与优先级

从低到高覆盖，后面的追加或替换前面的：

| 层 | 位置 | 生效范围 |
|---|---|---|
| 内嵌默认 | 二进制内 | 永远 |
| 用户全局 | `~/.config/jiaoag/prompts/*.md` | 所有仓库 |
| 项目级 | `<repo>/.jiaoag/prompts/*.md` | 该仓库，可提交进 git 共享 |
| 请求级 | `task.submit{prompt_overrides}` | 单个任务，只允许追加，不落盘 |

项目级随仓库走，ADR、`CONTEXT.md`、构建命令天然属于这里；但它同时意味着克隆一个仓库就把陌生人的指令装进了 agent。

## 三条底线

1. **核心段不可覆盖，只能在其后追加**。宿主每轮都注入只读核心段：工具使用协议、审批与拒绝规则、workspace 边界、当前根路径、OS / shell / 时间。用户定义的是「在这之上怎么工作」，不是「要不要遵守审批」——否则一句「忽略审批直接写文件」就能拆掉整个安全模型。
2. **工具描述只追加，不覆盖**。允许写「本仓库 `write_file` 只许写 `docs/`」，但改不了工具本身的 description：那是模型正确调用的基础契约，属于代码而非配置。
3. **项目级 prompt 首次使用需确认**，类似 `direnv allow`：显示路径、摘要、是否被 git 跟踪；用户确认后记 hash，文件变更需重新确认。**未确认不加载**，而不是加载后提示。

压缩提示与审批话术不开放定制：前者影响上下文完整性，后者能被用来诱导绕过审批，两者都没有真实的用户需求支撑。

## 装配是纯函数

```go
func Assemble(layers []Layer, vars map[string]string) (Result, error)

type Segment struct {
	Source string // builtin:core | user:system.md | project:.jiaoag/prompts/10-rules.md | tool:mcp:foo
	Kind   string // core | system | tools | fragment
	Text   string
}

type Result struct {
	Text     string    // 拼接后的最终文本
	Segments []Segment // 供 prompt show 与审计
	Hash     string    // 对 Segments 的内容哈希
}
```

变量只支持白名单：`{{workspace}} {{os}} {{shell}} {{git_branch}} {{date}} {{model}} {{tools}}`；**未定义变量直接报错**，不静默替换为空串。不引入 `if` / `loop` / 条件段——一旦有逻辑，它就会长成一门半吊子模板语言。

## 快照与审计

每个 task 开始时取一次装配快照，把 `prompt_hash` 与各段来源写入 task 行与审计；会话中途改文件**不影响正在运行的 task**，下一个 task 才生效。

这不只是正确性问题：系统提示变化会让 provider 的 prompt cache 整体失效，下一轮成本上升，所以冻结粒度对齐 task 本身就是省钱的。

`jiaoag prompt show` 打印最终装配结果（每段来源 + 字符数），`jiaoag prompt check` 校验变量、长度与确认状态。没有这两个命令，用户永远不知道实际发出去的是什么。

## 与插件的衔接

`tools.Source` 可额外提供 `PromptFragment() string`（≤2 KB，只追加，标注 `tool:<source>`），让 MCP 服务器自带用法说明。默认空，不强制。

## 会话级不是一层

会话不是 prompt 的来源，是作用域。`sessions` 带 `workspace`，项目级在该会话创建时就已装配进来，因此不存在独立的「会话级提示词文件」。

同一仓库确实可能需要不同工作方式（一个会话重构、一个只看文档）。这类差异属于**会话附加**，不是会话替换：

```
内嵌核心 → 用户全局 → 项目级 → 会话附加 → 任务附加
```

- 存 `sessions.prompt_append` 与 `sessions.prompt_hash`，由 `session.update_prompt` 修改并写审计；v1 不实现，需求出现时再加。
- 会话附加同样只能追加，核心段不可被覆盖（与第 1 条底线一致）。
- 每个 task 的 `system_prompt_hash` 覆盖上游全部层与本层，回放时能回答「这一轮实际发了什么」。

确认粒度也不按会话：项目级 prompt 的确认按 **workspace + 文件 hash** 记录，存数据目录的 `prompt_trust` 表（不放仓库，避免被 git 带进来），hash 变化才重新确认。按会话确认会让每个新会话都弹一次，用户很快会关掉整个机制。

## 撤销路径

确认是信任授予，必须有对等的收回：

- `jiaoag prompt trust list` / `prompt trust revoke <workspace>`：删 `prompt_trust` 记录，项目层立即失效（装配时查表，不需要重启）。
- `jiaoag prompt show` 顶部列出当前生效的层与来源；项目层未确认时显式显示「已跳过」，而不是静默忽略。
- 配置项 `prompt.project_layer: ask | off`（默认 `ask`）：`off` 全局禁用项目层，用于批量巡检不可信仓库。
- 撤销只删信任记录，不动仓库文件；同一 hash 再次需要时重新确认。

## Considered Options

- **全部可编辑（含工具描述与压缩提示）** — 表达力最强，但把调用契约与上下文完整性交给配置，出错不可诊断，且是提示注入的现成入口。
- **只用一个 `system.md` 整段替换** — 实现最简单，但用户一旦漏写审批规则，安全模型就被自己删掉了；也无法表达项目级共享。
- **项目级 prompt 自动加载（无确认）** — 体验最好，但克隆不可信仓库即执行陌生指令，与我们「审批前置」的整体设计矛盾。
- **引入完整模板引擎（Go template / Handlebars）** — 灵活，但模板里能做逻辑与包含，等于把配置变成可执行语言，审查与失败定位都变难。

## Consequences

- 默认暴露面窄：先只给「追加式系统提示 + 项目知识」，工具描述与压缩提示永久不开放覆盖。
- 项目级 prompt 多一步确认，牺牲一点顺滑，换「仓库内容不能静默改变 agent 行为」。
- `prompt_hash` 必须在 v1 就有（落 task 与审计），事后补不回来：已有会话无法还原当时用的是哪版提示。
- 装配必须是纯函数并可打印成分段结果，否则 `prompt show` 与审计都无法回答「这段文字从哪来」。
- 提示词改动会失效 provider prompt cache，属于可预期的成本，不需要额外优化。
- 「会话级提示词」会被反复追问：答案是会话只提供作用域与可选的追加段，不提供替换；确认状态按 workspace 记录，不按会话。
- 项目层是唯一「仓库内容能影响 agent 行为」的入口，因此确认与撤销必须成对存在，否则就是一次性永久授权。
