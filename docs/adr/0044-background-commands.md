# ADR-0044：后台命令绑会话，输出落日志，用 stop_command 收尾

- 状态：已采纳（v2.41）
- 日期：2026-11-25

## 背景

`run_command` 是阻塞执行：命令不退出，工具就不返回，最多 600 秒后超时被杀。`npm run dev`、`mvn spring-boot:run`、监听端口的服务因此跑不起来——agent 只能验证「编译通过」，无法验证「能启动」。

用户要求支持常规的「启动项目」，但明确不要把它做成一套独立的部署系统。

## 决策

1. **接口**：`run_command` 新增 `background: true`，与 `timeout_s` 互斥（后台进程本就不该被超时杀掉；同时给两个直接报参数错误）。`check_command` 不支持后台。
2. **返回**：启动成功立即返回，`tool_call_id` 就是后台 id；输出持续写入该调用的日志文件。`read_output` 用同一个 id 查看，`stop_command`（新工具）用同一个 id 停止。不新增 id 空间，事件与审计里的 `tool_call_id` 天然对得上。
3. **生命周期绑会话**：任务结束后进程继续跑；切换标签、客户端断线都不影响；会话删除、服务端 `Close`、空闲退出时按会话整体终止。重启不接管（与 ADR-0017 的「执行中任务不续跑」一致）。
4. **不算忙**：`HasBusyTasks` 只看 `running` 与真正在内存队列里的 `queued`，不看后台进程。否则一个 dev server 会让 `-exit-when-idle` 永远不触发。代价是「只剩后台进程」时服务端会退出并杀掉它们——这是刻意的取舍：没人连着的服务端不该替你看守进程。
5. **上限**：单会话并发 4 个，超出报错、不排队。退出后的条目保留在表里（`Running=false`），让 `stop` 幂等、日志仍可读；超过 4× 上限时清理最早退出的条目。
6. **输出**：只进日志文件，不进对话流。对话里只有一行启动/停止结果，避免 dev server 的刷屏淹没真正的工具结果。日志有上限（默认 4 MB），超限后丢弃并写一行提示。
7. **不施加资源限制**：后台命令跳过 `ulimit`/Job Object 的 CPU、内存限额——它们会把长驻服务直接杀掉。Job Object 仍用于「整树终止」；Unix 用进程组 `SIGKILL`。
8. **审计**：`exec.*` 的 detail 增加 `background: true`；`ExitCode` 为空（进程还没退出）。

## 后果

- 后台进程不是「托管服务」：没有自动重启、没有健康检查、没有端口管理。它只是「替用户把命令启动起来」。
- Windows 上关闭 Job 会连带收掉残留子进程（`KILL_ON_JOB_CLOSE`），Unix 的进程组只在显式 stop 时整组终止；父进程自行退出时 Unix 子进程可能留下，属于已知差异。
- 日志按 `tool_call_id` 定位，仍然不能读别的会话的文件（`read_output` 的既有约束）。

## 备选方案

- **新开 `start_command` 工具**：被否。模型已经熟悉 `run_command` + `read_output` 的组合，加一个字段的学习成本最低。
- **绑任务（任务结束即杀）**：被否。那就只能做「自测启动」，不能当 dev server。
- **进程独立于会话（只有显式 stop 才退出）**：被否。会留下没人认领的进程，空闲退出也永远走不掉。
- **输出流进对话**：被否。长驻进程的输出会淹没对话，且会撑爆上下文预算。
