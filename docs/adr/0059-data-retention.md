# ADR-0059：数据保留（`jiaoag admin prune` + `storage.retention_days`）

## 背景

`events` 与 `audit` 只增不删，长期运行的库会一直长大；此前唯一的办法是手写 SQL，而那等于绕过了删除的业务约束（顺序、外键、审计归属）。

同时，删除在这个系统里是个敏感动作：事件是会话回放的唯一来源，审计是追责依据。任何「按行删除」的方案都会留下残缺会话。

## 决策

1. **粒度是会话，不是行**。候选集合 = 所有任务已终态 + `sessions.updated_at` 早于保留期的会话；删除复用 `App.DeleteSession`（一个事务按序清任务/事件/审计/审批/提案/工具调用/会话授权）。
2. **手动命令 + 可选自动**。`jiaoag admin prune -older-than 90d [-dry-run | -yes]` 是唯一入口；`storage.retention_days > 0` 时运行时在启动与每 24 小时各跑一次同样的逻辑。
3. **默认不自动清理**（`retention_days: 0`）。删除是不可逆的，默认行为必须是「什么都不做」。
4. **确认门槛**：不带 `-dry-run` 也不带 `-yes` 时只打印计划并返回退出码 1，避免脚本里误跑。
5. **直接打开数据库**，不走 WS / 令牌 / 服务端。清理是低频运维动作，不该因为它要求一个正在跑的服务端；多运行时并发写已由 SQLite 写锁与 WAL 覆盖。
6. **删不掉就跳过**：会话在删除瞬间被提交了新任务会得到 `ErrSessionBusy`，命令继续处理其余候选并汇总报错；自动清理只记一条 Info。
7. **不碰输出文件与后台进程记录**：前者归文件系统策略，后者由 `/ps`（含孤儿校验）处理。
8. **保留期只认会话的最后活动时间**，不按单条事件时间做细粒度裁剪——那会切开一个会话的历史。

## 后果

- 库的增长可以靠配置封顶，且清理动作与「删除会话」走同一条代码路径，不会产生半删状态。
- 一个会话里个别很旧的事件会跟着会话留到最后；想要更细的粒度就得接受残缺回放，不做。
- 多运行时各自调度会重复尝试删除（幂等，代价是一次空查询）。
- 没有软删除 / 回收站：误删只能靠备份恢复。命令因此强制 `-dry-run` 与 `-yes` 两段确认。

## 备选

- **只删 audit 行**：留下「有操作、没记录」的任务，比不删更糟。
- **只删 events 行**：会话回放会残缺，破坏「事件日志是唯一事实」这条不变量。
- **按库大小/行数触发**：阈值型清理会在最不方便的时刻删数据，且难以解释删了谁。
- **内置定时器可配置周期**：多一个配置面，收益只是省一次 `cron`；24 小时固定节奏够用。
