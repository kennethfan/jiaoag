# ADR-0060：访问令牌落库、热更新与每令牌限速

## 背景

v2.17 的令牌方案是三件事拼起来的：

- 令牌只存在于 `config.yaml`（或它引用的文件）；
- 轮换 = 改文件 + `kill -HUP`；
- Windows 没有 SIGHUP，只能重启进程。

三个后果：轮换要碰配置文件且有短暂窗口；Windows 上「改完重启」意味着所有连接断开、正在跑的任务受影响；同一个令牌被拿去写脚本后没有任何用量约束，一个泄漏的只读令牌可以每秒几千次订阅把 CPU 打满。

## 决策

1. **令牌以数据库为准**。新增 `server_tokens`（name / hash / read_only / created_at / rotated_at / revoked_at）与单行 `server_token_meta.version`。配置里的 `server.token(s)` 只在「表为空」时导入一次，之后改配置不再影响认证——否则被轮换掉的旧值会在重启后复活。
2. **库里只存 sha256**。认证时把客户端明文哈希一次再常数时间比较。明文只在 `admin token create/rotate` 的输出里出现一次；泄露面因此少了「配置文件、备份、只读库副本」这一层（库副本里仍能看到哪些名字存在）。
3. **热更新靠版本号轮询**：服务端每 2 秒读一次 `server_token_meta.version`，变了就整体重载。Windows 与 Unix 同一套行为，不依赖信号。`SIGHUP` 保留为「别等那两秒，现在就重读」。
4. **全部吊销 = 拒绝一切连接**。这时清空内存令牌并返回错误，绝不退回配置里的旧值——「我不想让任何人进来」和「我读库失败」是两件事。
5. **新增 `jiaoag admin token list|create|rotate|revoke`**，直接打开数据库（与 `admin prune` 同一套理由：低频运维动作，不需要服务端、令牌或 WS）。令牌明文随机 32 字节 base64url（43 字符）。
6. **每令牌请求速率上限**：`server.token_rate_limit`（次/分钟，默认 600，`0` 不限），覆盖 WS 消息与需要令牌的 HTTP 抓取。用令牌桶按秒回填，超限 WS 回 `rate_limited` 错误帧、HTTP 回 429 + `Retry-After: 1`。`/healthz` 匿名探活不受限（它本来就不花队列成本）。
7. **权限仍定格在连接上**：令牌的 `read_only` 在握手时写进 `clientConn`，轮换/吊销不影响已建立的连接（断开要等客户端重连）。这是有意的——中途改变一条连接的权限会让正在跑的客户端行为不可预测。

## 后果

- 轮换操作变成「一条命令 + 等 ≤2 秒」，不再需要碰配置文件或重启；Windows 同样。
- 客户端（TUI / CLI / Web）仍从配置读令牌，所以轮换后要把新值写回配置或通过 `-token` 传。**这是这个方案唯一没解决的摩擦**：客户端没有「去库里取令牌」的能力，也不该有（那等于给每个客户端库访问权）。
- 库里只有哈希，忘记明文只能再轮换一次。
- 令牌不再能靠「删配置项」吊销——必须 `admin token revoke` 或直接改库。
- 限速是进程内的：多运行时各自计数，所以实际允许速率是 `limit × 运行时数`。单机自用够用；要严格全局限速得把桶也落库，代价不值得。
- 已建立的连接不受轮换影响，吊销后旧连接仍可用——需要立刻断开时，重启服务端（或等客户端重连）。

## 备选

- **保持配置文件为准 + 定时重读文件**：不引入第二份真相，但轮换仍要写文件、要处理「文件改了但解析失败」的半状态，且多运行时各自的配置文件视图可能不一致。
- **JWT / 短期签名令牌**：能自证有效期，但要引入签名密钥与刷新流程，单机场景是纯复杂度。
- **把令牌放进系统钥匙串**：宿主差异大，脚本化运维反而更难。
- **限速按连接而非令牌**：换一次连接就重置配额，起不到「约束这个令牌」的作用。
