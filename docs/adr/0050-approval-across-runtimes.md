# ADR-0050 审批跨运行时：裁决落库，等待方轮询

状态：已采纳（v2.48）

## 背景

ADR-0049 之后允许多个运行时同时使用同一个库（两个 TUI、TUI + serve）。
任务占位解决了「同一个任务被执行两次」，但审批还停在进程内存里：

- `app.approvalState` 用 `waiters` 记录哪个协程在等哪个审批；
- `ResolveApproval` 把裁决投进这个 map；
- 若任务跑在运行时 A、用户在 B 里点批准，B 只在自己的 map 里找不到等待者，
  于是把结果存进 `resolved`；A 的协程永远等不到，直到任务超时。

这是 P1 之后剩下的最严重的一个跨进程缺口：**用户看着界面按了批准，任务却
因为「批准落在另一个进程」而失败**。

## 决策

1. **`approvals` 表是裁决的唯一事实来源。** 内存里的 `waiters`/`resolved`
   全部删除；谁执行任务、谁批准都不再需要共享进程内存。
2. **裁决用 CAS 写入。** `UPDATE approvals SET decision=?, source=?, resolved_at=?, note=?, hunks=? WHERE id=? AND decision=''`；
   只有第一个写入者成功，第二个返回「没有落定」并按幂等处理（不报错、不覆盖）。
   「先读、发现为空、再写」会让两个进程都以为自己赢了，所以不用那种写法。
3. **等待方每 400ms 轮询。** `AwaitApproval` 先查一次会话白名单，再查一次
   审批，然后按 400ms 轮询 `approvals.decision`，ctx 取消立即退出。不引入
   跨进程通知通道（事件总线只在进程内，另建一套推送比轮询复杂得多，而审批
   是人工节奏）。
4. **块号随裁决落库。** hunk 级部分批准（ADR-0028）的 `hunks` 以前只存在于
   投递给等待者的内存结果里；新增 `approvals.hunks`（JSON 文本，空串=整份），
   另一个进程读回来的是同一份决定。
5. **`allow_session` 不变。** 它本来就落在 `session_approvals` 表并带过期
   （ADR-0030），跨进程语义已经正确；CAS 成功之后才写白名单，避免「别人批的」
   被重复记一次。
6. **启动清理跳过活着的运行时。** `ExpirePendingApprovals` 遇到「任务是别的
   运行时持有且心跳仍在」时跳过：这条审批有人等，结局由它自己写。否则新
   运行时一启动就会把别人正在等的审批标成过期。
7. **过期按失败处理。** 轮询读到 `expired` 时返回错误而不是「拒绝」：过期只
   发生在原协程已经不存在的清理场景，再走一遍拒绝流程会重复写结局。

## 后果

- 跨进程审批可用：在任一客户端批准，执行任务的运行时在 400ms 内继续。
- 每个等待中的审批每秒两次读库；审批是低频操作，代价可以忽略（WAL 下是
  纯读）。任务很多且都卡在审批时会有可观测的读放大，但不会写放大。
- 裁决一旦落库就不可改（CAS 语义）；要改只能重新发起一次工具调用。这与
  「一次调用一次审批」一致。
- `approvals` 表多了 `hunks` 列（迁移 0008），旧库升级时默认空串，语义是
  「整份应用」。
- 仍未跨进程：流式 delta（只在本进程 hub）、后台进程（P3）、MCP/插件子进程
  （每个运行时各自起一份）。

## 备选

- **裁决走事件总线广播**：hub 只在本进程，跨进程要么加 SQLite 通知表、要么
  加 UDS，复杂度明显高于 400ms 轮询。
- **保留内存等待者 + 落库双写**：两份事实来源，冲突时无法判定谁对；且仍然
  需要轮询兜底。
- **让批准请求绑定到执行进程**：需要客户端知道任务在哪个运行时，把「用户
  点了批准」变成一次路由问题，体验更差。
- **把审批改为共享内存/文件锁**：回到 ADR-0048 被否掉的方向。
