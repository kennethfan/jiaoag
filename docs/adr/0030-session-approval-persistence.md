# ADR-0030：allow_session 授权落库并带过期

## 背景

`allow_session`（TUI 里按 `a`）的语义是「这个会话内，同样的工具 + 同一段参数不用再问我」。它原先只存在进程内存里，代码注释甚至明确写过「不落盘」的理由：怕它变成一条永久豁免。

真实使用暴露了代价：一次 `kill -HUP` 之外的重启、一次版本升级、一次崩溃，全部已经表过态的授权一起消失，同样的 `cat -u notes.txt` 又要问一遍。用户每天重复裁决同一件事，审批就从「有人负责」退化成「按 y 的手速练习」。

## 决策

1. **授权存 `session_approvals` 表**：`(session_id, key)` 为主键，`key` 是「工具名 + 参数原文」的 sha256（与原先内存实现同一算法）。参数原文不同就是另一次请求，宁可多问一次也不误放行。
2. **带过期时间，默认 12 小时**（`agent.approval_ttl`，接受 `12h` / `30m` 这类写法）。它是一次便利，不是永久豁免；过期后同样的调用会重新询问。
3. **读取时判过期**，不依赖后台清理：`expires_at > now` 才算命中。这样即使清理协程没跑，过期的授权也不会生效。
4. **写入时顺手清理**已过期行，避免表只增不减。另有 `PruneSessionApprovals` 供将来接定时任务。
5. **读失败按未授权处理**（fail closed）：多问一次比误放行安全。真正的写失败（`RememberSessionApproval`）会作为 `ResolveApproval` 的错误返回给客户端。
6. **授权仍是会话维度**：不同会话互不可见。跨会话复用同一个 MCP server 不等于复用审批。
7. **TTL 在启动时定死**：改配置需要重启，运行中的新授权沿用旧值；已有记录按自己的 `expires_at` 生效。
8. **不新增事件类型**：放行依旧产生 `approval.requested` 与 `approval.resolved`（`source=policy`），审计链路不变——「自动放行」也是一次决定，必须留痕。

## 后果

- 重启后同一会话的同类调用不再弹审批；用户不用重新教育 agent。
- 授权的有效期是运维参数：默认 12 小时对「一个工作日内的连续调试」够用，对长期驻留的会话则会在一天后重新确认一次。
- 数据库里多了一张小表；`session_approvals` 的过期行靠写入时清理，长期只读的实例可能留下少量历史行（不影响正确性，读取已按时间过滤）。
- 语义仍不是「这个文件永远可以改」：键里含参数原文，diff 内容或 argv 变化都会重新询问。

## 备选方案

- **保持纯内存**（原状）：最安全，但重启即清零，用户重复裁决的成本高。
- **落库且不过期**：等于把「本会话内」变成「永远」，与 ADR-0001 的「每次写入都要有人负责」直接冲突，不采纳。
- **按工具而非按参数授权**（「这个会话内 write_file 都放行」）：粒度太粗，一次放行等于放弃整类操作的审阅。
- **落到会话行上的 JSON 字段**：省一张表，但清理与过期判定都要在应用层做，还得处理并发更新，不如独立表直接。
