# 上下文压缩：把较早轮次摘成一条事件

长任务里，模型上下文随轮次线性增长：每一轮的工具结果都留在历史里，预算一满就只剩「丢最旧的」这一招。丢掉的恰好是任务目标、已定的约束和踩过的坑，于是 agent 开始重复犯错。本文落下 v2 的第一版语义压缩：超预算时把较早轮次交给模型摘要，摘要作为一条**事件**进入日志。

## 背景

v1 的 `Build` 是纯函数：在字符预算内保留 system、最后一条用户消息和尽量新的轮次，超出就整段丢弃（`TruncateOldest` 的等价物）。这是止血，不是记忆：

- 丢弃不可逆，回放时看不出「曾经知道什么」；
- 被丢的往往正是任务早期确立的目标与约束；
- 工具结果占字符最多，却也是「哪条路走不通」的证据。

架构文档 §12.2 曾预留 `Compactor` 接口，但按「只缓存不入库、只写审计」设计。实现时改变了这一点，理由见决策 2。

## 决策

1. **触发条件是预算的 80%，保留最近 2 轮。**
   `agent.context_budget_chars` 的 80% 是压缩阈值，留 20% 给本轮请求与摘要本身。切点按「用户提问」找：保留最后 2 个任务边界，切点之前的消息进摘要；同一任务内没有新提问时退到助手消息边界，绝不切开 `tool_use` / `tool_result`。切出来的旧内容不足 2000 字符就不值得一次模型调用，直接跳过。

2. **摘要是一条 `context.compacted` 事件，不是旁路缓存。**
   事件携带 `summary`、`covered_messages`、`before_chars`、`summary_chars`、模型与 token、耗时。回放时 `messagesFromEvents` 用摘要替换被覆盖的前缀，再接上保留的近期消息——重建出的上下文与压缩当时一致。这样做的代价是摘要进入事件日志；收益是**压缩本身可回放、可审计、可解释**，不需要第二份状态，也不需要按 seq 区间复用摘要的缓存表。

3. **摘要由当前 provider 生成，独立超时，失败不影响任务。**
   `providerCompactor` 发一次非流式 `Chat`：system 提示要求保留目标、约束、决策、涉及的文件与命令、错误与未完成步骤；历史按角色渲染，单条工具结果截到 2KB，总输入截到 48KB。超时 90s，`max_tokens=1024`。失败只写 `context.compact_failed` 审计并继续用原历史——压缩是优化，不是运行前提。

4. **冷却 3 轮，避免每轮都压。**
   压缩成功后 3 轮内不再尝试。否则「摘要 + 近期消息」仍可能贴着阈值，导致每轮一次额外的模型调用。

5. **摘要 token 计入任务用量。**
   压缩调用的 prompt / completion token 通过同一条 Transition 的 `Usage` 累加进任务，审计里也留一份。压缩不是免费操作，成本必须可见。

6. **摘要在预算裁剪中不被丢弃。**
   `Build` 把位于首条的摘要钉住，先对剩余消息做预算裁剪，再把摘要放回最前。否则预算紧张时刚生成的摘要会被自己的裁剪逻辑丢掉。

7. **默认开启，可显式关闭。**
   `agent.context_compact: auto`（默认）/ `off`。关闭后行为回到 v1：只按预算丢弃。摘要提示属于代码，不开放配置（架构 §12.5）。

## 后果

- 长任务的目标与约束能以千字以内的摘要活过预算，而不是被整段丢弃。
- 事件日志多了一种类型；任何按 `EventKind`  exhaustive 的地方（回放、TUI、未来的导出器）都要处理它。
- 摘要质量取决于模型：它可能漏掉细节或写错结论。因此摘要只作为「较早对话」的提示，不替代工具结果的原始审计；需要精确事实时仍应重新读文件。
- 压缩调用增加一次模型请求，且发生在任务中途；provider 故障时任务继续，但上下文压力仍在，后续轮次会继续按预算丢弃。

## 备选方案

- **只写审计、不入事件**（架构文档原计划）：回放重建不出压缩后的历史，断线重连会看到压缩前的完整上下文，与运行中的任务不一致；要实现一致就得引入 `compactions` 表按 seq 复用，多一份状态。否决。
- **本地启发式摘要**（抽首尾句）：不耗 token，但质量不足以保留约束与错误，容易留下误导性的半句话。
- **固定窗口 + 文件化记忆**：把旧轮次写到工作区文件再引用。引入新的写入面与审批问题，留到「长期记忆」单独立项。
- **每轮都压缩**：成本高、抖动大，且会把近期决策也压成摘要。
