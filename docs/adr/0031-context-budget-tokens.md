# ADR-0031：上下文预算按估算 token 计

- 状态：已采纳（v2.19）
- 日期：2026-11-24
- 相关：ADR-0016（上下文压缩）、ADR-0012（提示词分层）

## 背景

v1 的上下文预算用 **UTF-8 字符数**（`agent.context_budget_chars`，默认 60000），
理由是「无依赖、可测」。代价是同一个配置在不同任务上差出几倍：

- 中文一字一 token 左右，60000 字符≈60000 token；
- 英文约四字符一 token，60000 字符≈15000 token；
- 代码与 JSON 夹着大量标点，介于两者之间但更接近英文。

也就是说，一个跑中文文档的任务会在 60k token 处被截断，而同一个预算跑英文代码
还剩四分之三没用；反过来配得刚好够英文时，中文任务早就撞供应商的上下文上限。

供应商确实会在响应里回 `prompt_tokens`，但那是**事后**才知道的——不能用来决定
这一轮该发多少。而没有任何供应商提供可离线、可复现的分词器（Anthropic 明确不
提供），所以「精确」这条路线从根上走不通。

## 决策

1. **预算单位改为 token 估算**，配置项 `agent.context_budget_tokens`，默认 32000
   （约等于原 60k 字符在混合内容下的实际占用）。
2. **估算按字符类别加权**：ASCII 字母数字与空白约 4 字符/token，ASCII 标点约
   2 字符/token，CJK（汉字、假名、谚文、注音）约 1 字/token，其余非 ASCII 取
   0.75。每条消息、每个内容块另加固定结构开销（角色标记、`tool_use` 包装）。
3. **用真实用量在线校准**：每轮成功响应后用 `prompt_tokens / 估算值` 作为样本，
   按权重 0.3 更新系数（EWMA），系数夹在 `[0.5, 3]`。估算不足 200 token
   的请求不参与校准——固定开销占比太大，比值没有参考价值。
4. **固定开销先扣掉**：系统提示与工具清单每轮都要发，`消息预算 = 总预算 −
   overhead(system, tools)`，下限 512 token。工具多的会话不会等到真超限才发现
   预算早就不够。
5. **压缩阈值复用同一估算**：ADR-0016 的 80% 触发、`minCompactOldTokens = 800`
   都改为 token 口径；`BeforeChars` / `SummaryChars` 仍以字符记录，因为那是给
   人看的指标，不是用于决策的门槛。
6. **旧配置保留兼容**：`context_budget_chars` 仍可写，未配 token 预算时按
   **2 字符/token** 折算；两者都配以 token 为准。这样老配置不会因为换单位而
   突然把上下文砍半或翻倍。
7. **不引入 tokenizer 依赖**：tiktoken 之类只对 OpenAI 系精确，打包几十 MB 词表
   换来「一半精确」，而且模型换代就得跟着换表。启发式 + 在线校准对两家都用同一
   套逻辑，误差由真实用量收敛。
8. **超限重试仍然减半**：`ErrContextOverflow` 时预算折半、下限 512 token，只重试
   一次。换算单位不改变这条兜底。

## 后果

- 同一个预算在中文、英文、代码任务上的实际余量接近，不再随内容语言漂移。
- 估算仍然会错：新会话第一轮没有校准样本，用的是初始系数。偏差在头一两轮就会
  被真实用量纠回来；代价是极端内容（例如全 emoji）第一轮可能偏保守。
- 校准发生在**失败前**：如果第一轮真的超了供应商上限，走的是既有的 overflow
  重试路径，而不是等校准。
- 预算数字的含义变了：从「字符」变成「token 估算」。文档与 `example.yaml` 都
  标明了单位折算关系，`jiaoag-events` 导出的审计里 `before_chars` 仍是字符。
- 没有引入新依赖，二进制大小不变。

## 备选方案

- **集成 tiktoken-go**：OpenAI 系精确，Anthropic 仍要估；多一个依赖与词表，
  且误差从「两家都估」变成「一家精确一家估」，复杂度不划算。
- **固定 2 字符/token**：实现最省，但中文被低估近一倍——正是本次要修的问题。
- **按字节数**：中文三字节一字，比字符数更偏；英文则与字符数接近，没有改善。
- **让用户填模型的真实上下文窗口，按窗口百分比算**：看起来更自然，但用户往往
  不知道供应商给的是输入上限还是总上限，且不同模型差异大；预算本来就该由用户
  按成本意愿配。
