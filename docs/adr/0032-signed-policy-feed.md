# ADR-0032：签名规则 feed

状态：已采纳（v2.20）

## 背景

`policy.d/*.yaml` 让用户自己收紧规则，但有一类收紧是用户写不出来的：某个程序
的哪个 flag 能绕过审批、某个包昨天有没有被投毒。这些是持续变化的外部事实，
推不出来，只能订阅。

订阅就要回答三个问题：

1. 来源可信吗——中间人能不能改规则内容；
2. 能不能被拿来回滚——攻击者重放一份旧的「很宽松」的 feed；
3. 最坏情况下会不会放宽——如果 feed 能写 allow 规则，那它就是一个远程放行通道。

第三条决定整个设计的形态：**feed 只能是收紧规则**。这一点由 `perm.Loader`
强制（外部规则一律 `Tighten = true`），不靠发布方自觉。于是第 1、2 条失败时，
最坏后果只是「多要几次审批」，而不是「任意命令免审」。

## 决策

1. **形态**：`feed.yaml`（普通规则文件）+ `feed.yaml.sig`（分离签名，ed25519，
   base64 文本）。签名覆盖 feed 的完整字节，`version` / `issued_at` /
   `expires_at` 都在签名范围内。选分离签名而不是内联：规则内容保持可读、可 diff、
   可以用 `base64 -d` 手工核验。
2. **信任根**：`policy.feed.keys` 里的 ed25519 公钥（base64），可配多把用于轮换。
   `url` 与 `keys` 必须同时配置——只配一半会让「我以为有签名保护」静默落空，
   比不用 feed 更危险。
3. **生效路径**：新增 `jiaoag-policy sync` 手动同步——下载 → 验签 → 检查有效期 →
   挡回滚 → 原子写入 `policy.d/`。服务端**只读本地文件，不主动出网**。理由：
   单机工具的默认网络行为应当是「什么都不发」；更新时机应该显式。
4. **回滚保护**：`policy.d/feed.state` 记录上次成功安装的 `issued_at` 与内容摘要。
   新 feed 的 `issued_at` 必须严格晚于已安装的那份；内容相同则视为「已是最新」。
   只比版本字符串不可靠（命名是发布方的自由），签发时间才可比较。`-force` 可
   显式绕过回滚保护（例如误发了未来时间戳）。
5. **有效期**：`expires_at` 过期后 `sync` 拒绝安装、服务端启动拒绝加载。宁可让
   人看见「规则过期了」，也不让人以为还在保护中。`-force` 可安装过期 feed。
6. **顺序与版本**：feed 规则排在本机 `policy.d/*.yaml` 之后（本机规则是用户明确
   写的，先匹配），规则集版本拼成 `builtin-2+feed@<version>`，`policy_hash`
   随内容变化——审计里的 `policy_version` 能直接看出某次判定用的是哪份 feed。
7. **只读本地**：服务端不做自动拉取、不做定时刷新。要生效就是「跑 sync，重启
   服务端」；`jiaoag-policy -verify` 可离线校验已安装的 feed。
8. **失败不静默**：签名错、缺签名、过期、格式坏，一律报错并拒绝启动；不会
   「跳过 feed 继续跑」。

## 后果

- 规则更新不是即时的：从发布到本机生效至少需要一次 sync + 重启。
- 没有增量协议：每次同步整份文件（上限 1 MB）。
- 公钥轮换要人工：新旧公钥同时在 `keys` 里放一段时间。
- 过期策略偏严：长期不联网的机器会在 feed 过期后无法启动，需要重新 sync 或
  删除 feed 配置。这是刻意的——「以为有保护其实没有」更糟。
- feed 仍然只是收紧：它不能放行任何东西，也不能改判定顺序。

## 备选方案

- **服务端自动拉取 + 定时刷新**：更新更及时，但服务端会主动出网，且引入
  「什么时候拉、失败怎么办、要不要告警」一整套状态。先手动，确有需求再加。
- **内联签名块**（`payload: base64` + `signature`）：单文件好分发，但内容不可读，
  失去 diff 与人工核验的价值。
- **minisign / signify**：复用现成工具链，但要引入外部二进制依赖，且输出解析
  容易随版本漂移。
- **不签名，只接受 https**：省掉密钥管理，但无法防镜像源被替换，也无法离线分发。
- **允许 feed 写 allow 规则并配白名单校验**：复杂度高，且与「外部数据只能收紧」
  的既有边界冲突。
