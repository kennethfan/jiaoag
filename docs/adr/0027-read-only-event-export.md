# ADR-0027：事件与审计的只读导出通道

- 状态：已采纳（v2.15）
- 日期：2026-11-24
- 相关：ADR-0005（事件日志与回放）、ADR-0006（审计表）、ADR-0008（协议）

## 背景

审计与事件都只落在本地 SQLite 里。想接日志系统、CI 或事后复盘，只能拿 `sqlite3` 手写 SQL，而且：

- 远程部署（开了 TLS、跑在另一台机器）时根本没有入口；
- 审计表没有 `task_id` / `session_id` 列，关联要自己写 JOIN；
- 想「跟着看正在发生什么」没有工具——TUI 只显示当前会话，且面向的是操作而不是导出。

事件流本身有 `event.subscribe`，但它是为客户端重连设计的：没有「只要新事件」的轻量入口，也没有跨会话的审计增量。

## 决策

**新增一个只读客户端 `jiaoag-events`，走现有 WS 协议，服务端只加两个只读命令。**

1. **`event.head`**：返回会话当前最后的事件序号。消费者据此实现「只看新事件」（默认行为），而不必先全量回放再丢弃。`event.subscribe` 原样复用，回放 + 增量 + 快照语义不变。

2. **`audit.tail`**：按 `audit.id` 游标升序取记录，`after_id` 为负时只返回当前水位（`next_id`），不返回记录——这就是 tail 的「从现在开始」。审计是追加表、id 单调，天然适合游标；不引入推送通道，客户端按 `-interval` 轮询（默认 1 秒）。

3. **审计与任务的关联在读取侧做**：`ListAudit` 用 `LEFT JOIN tool_calls → tasks` 补出 `task_id` / `session_id`。用 `LEFT` 是因为不是每条审计都有工具调用（`context.compact` 就没有）；关联不上也要导出，导出侧不能因为 JOIN 失败就丢审计。

4. **只读，没有写入口**：不提供删除、修订、重放触发。审计是事后追责的依据，导出通道一旦能写就失去意义。协议侧只有读命令，客户端也不带任何 `task.*` / `approval.*` 能力。

5. **输出以 JSONL 为准**：每行一个对象，`kind` 区分 `event` / `audit`，字段稳定，可直接给 `jq`、Fluent Bit、CI 日志。`-format text` 只给人看，长载荷会截断，不承诺字段稳定。

6. **`-until-now` 按启动时刻截断**：导出时记下两个 head（事件 seq、审计 id），追平即退出，之后产生的不追。这是定时导出的正确语义——否则任务一直在跑就永远导不完。

7. **不做**：跨会话事件通配订阅（要改 hub，且多会话监控当前没有需求）、审计后处理/告警规则（属于消费方职责）、HTTP 拉取接口（WS 已够，且多一套鉴权面）。

## 后果

- 审计第一次有了可远程、可脚本化的出口；`docs/observability.md` 给出 tail / 导出 / 定时三类用法。
- `audit.tail` 的轮询间隔是导出延迟的下限（默认 1 秒）；要更低延迟得加推送，暂不做。
- 事件是**单会话**的：`jiaoag-events` 默认取最近活跃会话，多会话要起多个进程。这是刻意的——全局事件流需要一个全局序号，而 seq 是按会话分配的。
- 审计 id 全局单调，因此同一进程里可以同时导出多个会话的审计而事件只跟一个会话；文档里写清了这一点。
- `ListAudit` 是只读查询，不影响事务路径；`audit` 表结构与写入路径未改。

## 备选方案

- **直接读 SQLite**：零协议改动，但只能本机、绕过鉴权，且与「远程部署」方向相反。适合临时排查，不作为产品入口。
- **把审计当事件写进事件流**：能让一个订阅拿到全部信息，但审计是「事实记录」、事件是「状态流」，混在一起会污染回放语义（客户端重放时会看到审计帧），也改动了 ADR-0005 的不变量。
- **全局事件通配订阅**：多会话监控台才需要；当前会引入全局序号或每会话游标的复杂度，先不做。
- **HTTP `/events` SSE**：浏览器友好，但多一套鉴权与连接管理；WS 已经在跑。
