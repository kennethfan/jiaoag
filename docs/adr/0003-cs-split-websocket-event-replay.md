# 客户端与服务端分离，长连接同时承载事件流与审批

服务端持有会话、任务与工具执行，TUI 客户端只负责渲染与裁决；两者通过网络长连接通信，而不是同一进程内的两个 goroutine。

选它有三个具体理由：审批必须能从服务端主动推给客户端、并在极短路径上拿到用户决定，否则 HITL 会退化成轮询；客户端断开后任务要继续跑，重连时按**事件**序号回放缺失部分；协议按可远程设计，首版虽然客户端与服务端同机跑在 localhost，但搬到别的机器时不需要重写。

## Considered Options

- **单进程先跑通** — 交付最快，但审批与流式输出会直接耦合进 UI 代码，C/S 拆分反而要重写一遍。
- **REST + SSE** — 下行流式够用，但审批与中断得另开接口，且多会话事件多路复用会变复杂。
- **gRPC 双向流** — 语义最严谨，但单人项目的代码生成与调试成本不划算。

## Consequences

- 事件需要会话内单调序号，所有客户端状态都必须能从事件流重建。
- 任务的生命期与连接解耦：断开即取消是不允许的语义。
- 首版鉴权只需一个本地 token，但协议里必须留位置，否则远程部署时要改协议版本。
