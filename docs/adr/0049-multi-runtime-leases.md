# ADR-0049：多运行时调度——任务占位与租约

- 状态：已采纳（v2.47）
- 日期：2026-11-26
- 相关：ADR-0007（任务状态机）、ADR-0019（空闲退出）、ADR-0048（内嵌运行时）

## 背景

ADR-0048 用文件锁（`runtime.lock`）保证「同一数据目录只有一个运行时」。但用户指出：SQLite 本来就是多进程数据库，WAL + `busy_timeout` 下同时写并不会坏。

真正怕的不是并发写库，而是**运行时状态只在进程内存里**：

| 状态 | 双运行时后果 |
|---|---|
| 任务队列 / 并发槽 | 两个进程各自从库里捞 `queued`，同一任务执行两次 |
| 审批等待者 | A 的任务等审批，B 里批准 → 结果进了 B 的内存 map，A 永远等不到，只能超时 |
| 事件广播 | B 的客户端订阅不到 A 的事件 |
| 后台进程表 | 互相停不掉，留下孤儿进程 |
| schema 迁移 | 同时启动会撞锁 |

文件锁把这些全部掩盖了，代价是第二个 TUI、或 TUI 与 `serve` 不能并存。

## 决策

1. **任务占位（claim）放在数据库里**
   启动一条 `queued` 任务前，用一条 `UPDATE` 同时写入 `owner` 与 `lease_until`，
   条件包含「目标仍是 queued 且无 owner」「同会话没有 running / waiting_approval /
   未过期的保留任务」「全局 running 数小于并发上限」。SQLite 的写串行保证只有一个
   运行时的 `RowsAffected=1`，一条语句同时实现互斥、会话串行与并发上限。

2. **租约续期与接管**
   执行期间每 10 秒续租，TTL 60 秒。续租覆盖 `waiting_approval`——等人批十小时也
   不该被当成失联。过期任务由任意运行时的维护循环接管，标
   `failed(owner_lost: 运行这个任务的进程已失联，任务未完成)`，**不重新入队**：
   重跑一个可能已经产生副作用的任务比失败更危险。

3. **终态立刻释放占位**
   任务进入 completed / failed / canceled 时，同事务把 `owner` 与 `lease_until` 归零；
   否则同一会话的后续任务要等 60 秒租约过期才能被别的运行时捡起来。

4. **运行时注册表**
   `runtimes(id, pid, host, kind, started_at, heartbeat_at)`，每 5 秒心跳；
   30 秒无心跳视作失联。`kind` 只用于观测（`tui` / `serve`），不影响调度。

5. **删除文件锁**
   `boot` 不再创建 `runtime.lock`；`ErrLocked` 与 `lock_*.go` 移除。第二个 TUI 与
   `serve` 都可以启动。

6. **启动不再互相踩**
   迁移遇到 `SQLITE_BUSY` 时退避重试最多 30 秒；数据库连接加 `_txlock=immediate`，
   避免「读后写」事务在升级写锁时直接返回 BUSY（这种 BUSY 不遵守 busy_timeout）。

7. **启动收尾不再误杀别人的任务**
   `ReapUnfinished` 遇到 owner 是另一个仍然存活的运行时，就跳过——不能把别人正在
   跑的任务标成 canceled。

## 后果

- 两个内嵌 TUI、TUI + `serve`、多个 `serve` 可以同时使用同一个数据目录。
- 崩溃恢复语义是 at-most-once：宁可失败也不重跑（与 ADR-0017 的 queued 续跑不同，
  那里任务还没开始，重跑安全）。
- 「谁在跑」变成可观测的：`SELECT id, status, owner, lease_until FROM tasks`。
- 仍在内存里的部分（P2/P3 未做）：
  - **审批等待**：`AwaitApproval` 目前仍轮询进程内 map；跨进程批准要等 P2。
  - **事件**：只有执行任务的运行时能推送该任务的实时事件（含 `assistant.delta`）；
    其他进程要从数据库 tail（P3）或重新订阅回放。
  - **后台进程**：`ProcTable` 仍是进程内表；别的运行时停不掉（P3 落库）。
- 空闲退出只认「库里 running」与「本进程还有真排队的任务」，不因为「另一个运行时
  活着」而拒绝退出。
- 并发启动时迁移只应用一次：每个迁移在写事务内先复核 `schema_migrations` 的最大
  版本号（`_txlock=immediate` 已持写锁），后到的运行时看到已应用就直接跳过，不会
  因为两边都读到 `current=0` 而重复执行 0001。

## 备选

- **保持文件锁**：改动最小，但第二个 TUI / serve 永远不能并存，用户明确否决。
- **只把队列落库、不落租约**：崩溃时无法区分「正在跑」与「进程已死」，会卡死或重跑。
- **每次任务都重新查 owner 而不是租约**：进程崩溃后 owner 行还在，无法判定存活。
- **把调度交给独立 daemon**：等于永远 serve，与「TUI 纯本地」的目标冲突。
