# ADR-0024：用户显式指定技能，正文确定性地进入该任务

日期：2026-11-23
状态：已采纳

## 背景

ADR-0023 把技能做成「索引常驻、正文按需」：模型看得到名字与适用场景，判断相符时自己调 `skill` 工具取正文。

这套机制有两个洞：

- **`disable-model-invocation: true`**。技能库里有相当一部分技能（本机 matt 系列 `ask-matt` / `grill-me` / `grill-with-docs`）带这个字段，语义是「只能用户手动敲，模型不许自己调」。原实现只解析 `name` / `description`，于是这些技能照样进了索引、照样会被模型自动挑中——语义正好相反。
- **用户想点名时没有入口**。用户看到某个技能、明确知道这次要用它，唯一办法是在 prompt 里写「请先调用 skill 工具加载 grilling」——依赖模型配合，多一次往返，还可能挑错或干脆不调。

## 决策

- **解析 `disable-model-invocation`**：值为 true / yes / on / 1 时把技能标记为 `Manual`。这类技能**不进模型索引**，只在索引末尾留一句「另有 N 个技能标记为仅手动调用」，让模型知道存在但不可自选。
- **`Manual` 不影响可加载性**：`skill` 工具仍然能读它，`/skill` 面板也照常列出，标 `[仅手动]`。字段约束的是「模型自选」，不是「不可用」。
- **用户侧入口 `/skill`**：`/skill` 向服务端要技能列表（`skill.list`），弹面板，`↑↓/jk` 选、`enter` 指定、`x` 清除。带参数的 `/skill <name>` 直接指定，不弹面板。指定后状态行显示「技能 grilling」，下一条任务生效。
- **确定性注入而不是「请模型去调」**：指定结果随 `task.submit` 的 `skills` 字段上行，服务端在建 agent 前把正文直接拼进系统提示（`user:skill:<name>` 层，位于技能索引之后、记忆之前）。模型不需要自觉，也不会挑错。
- **注入的内容与 `skill` 工具返回一致**：同一个 `Catalog.Body()`，含绝对基准目录与一级目录清单。两条路径不产生两种口径。
- **只在提交时解析一次**：`task.submit` 里的名字必须能在**服务端**技能库中找到，找不到直接拒绝（`bad_request`，错误带名字），任务不落库。避免「任务已排队但技能加载失败」这种半状态。
- **上限 4 个**：`maxTaskSkills`。超过报错；重复名去重。
- **记进任务行**：`tasks.skills`（JSON 文本，迁移 `0002_task_skills.sql`），随 `task.queued` 事件一起可见，重启续跑时按原样重新注入。
- **进提示词 hash**：指定的正文改变 `system_prompt_hash` / `extensions_digest`，与 ADR-0023 的索引一致，任务提交时冻结。

## 后果

- 用户点名 = 一次打断、零往返。技能正文在第一轮请求里就在，模型不会先读索引再决定。
- `disable-model-invocation` 的语义被正确实现：模型看不到这些技能，也就不会「自作主张」地用。
- 任务行多一列、协议多两个消息（`skill.list` / `skill.list.result`）、TUI 多一个面板——都是显式成本。
- 技能库只在服务端扫描，所以 `/skill` 列的是服务端的技能。远端 server 的情况下客户端不参与解析，这是有意的：客户端不该决定服务端能加载什么。
- 一次任务最多 4 个技能正文，再多的组合请分任务。

## 备选方案

- **只在 prompt 里提示模型去调 `skill`**：不改协议、不改表，但依赖模型配合，且对 `Manual` 技能无效（模型不该自选，而用户又没法强推）。
- **把指定写成 `task.submit` 的一段文本前缀**（如 `/skill grilling` 原样保留在 prompt 里）：实现最省，但服务端无法校验、无法进 hash、无法在续跑时复原。
- **让客户端读技能目录、自己拼正文**：省一次服务端往返，但把技能解析分散到两个进程，且远端 server 场景下客户端的工作区与服务端不是同一个。
- **把 `Manual` 技能从索引里彻底删掉（连计数都不提）**：模型完全不知道它们存在，用户也没法从对话里发现。留一句计数是更好的折中。

## 修订（v2.45）：仅手动技能同时是斜杠命令

`disable-model-invocation` 的技能原先只能经 `/skill <名字>` 或面板指定，再输入问题——两段式，和它们「只能用户点名」的定位不匹配。现在给它们加一个命令式入口：

- 会话建立后拉一次 `skill.list` 缓存技能清单（服务端决定有哪些，含项目级 `.jiaoag/skills`），补全列表 = 内置命令（在前）+ `Manual` 技能（标 `技能`）。
- `/技能名 问题` 一步提交：正文仍走 `task.submit.skills`，服务端照旧解析并拒绝未知名字；`/技能名` 不带参数则先指定。
- 重名时内置命令优先，技能名不顶掉真命令；非 `Manual` 技能不进补全（仍由模型自选或 `/skill` 面板指定）。
- 一次性语义不变：提交后清空，不做粘性——正文最多 96 KB，误触的代价是按任务计费。
