# ADR-0026：传输加密（可选 TLS/wss）

## 状态

已采纳（v2.14）。

## 背景

服务端从 v1 起就是明文 HTTP + Bearer token，只监听 `127.0.0.1`。协议与客户端一直
按「可远程」设计，但传输加密一直空缺（§12.4 的部署空白之一）。

这带来两个现实问题：

1. **远程不可用**：把 `listen` 改成对外地址就等于把 token 明文发出去。token 是唯一
   身份凭据，拿到它就能读写工作区、执行命令、批准审批——没有第二条防线。
2. **靠反代是默认答案但不总是可用**：有现成 nginx/Caddy 时反代终结 TLS 更省事，
   但单机直连、内网临时排障、容器里直接暴露端口这些场景没有反代。

## 决策

1. **opt-in，不自动生成证书**：`server.tls_cert` 与 `server.tls_key` 同时配置才启用；
   默认仍是明文回环。不在启动时自签一张证书——自签证书默认不被信任，自动生成只会
   制造「连不上但不知道为什么」的体验。
2. **只配一半直接启动报错**，证书无法解析也在监听前报错。理由：静默退回明文是
   安全特性里最坏的一种降级（与 ADR-0011 的「降级必须显式」同一条原则）。
3. **同一个监听**：`healthz` 与 `/ws` 共用端口，启用 TLS 后两者都只在 TLS 上提供，
   不额外开一个明文端口。
4. **客户端按配置推导 scheme**：不传 `-url` 时，TUI 依据 `server.tls_cert` 选 `wss://`。
5. **`-insecure` 是显式客户端开关**，只用于自签证书；默认仍走系统信任链。不做
   「记住上次跳过的证书」这类便利，信任决定应当是每次都可见的。
6. **关闭时不发 close 帧**：`Close` 会等对端回话，卡住的客户端能把
   `http.Server.Shutdown` 拖满宽限期，而此刻再 `CloseNow` 已无效（关闭状态已被占用）。
   进程退出时直接断连，客户端按断线重连处理。

## 后果

- 远程部署可以不加反代，直接 `wss://host:8787/ws`。
- 证书生命周期（续期、SAN 变更）由部署方负责，代码只做加载与校验。
- 仍是单用户单 token：TLS 解决窃听，不解决授权模型。
- 数据库与输出文件仍是本地明文。
- 反代方案继续有效，且更推荐用于公网（证书轮换与访问日志在反代侧）。

## 备选方案

- **强制 TLS（无明文模式）**：会让本机开发与 `make demo` 都要维护证书，收益不抵成本。
- **自动生成自签证书**：省一步，但把「不被信任」的坑推给用户，且难以轮换。
- **内置 ACME 自动签发**：需要域名、80/443 端口与持久化账户状态，超出单机 agent 的范围。
- **mTLS / 多 token / 按会话授权**：属于授权模型，不是传输层；单独立项。
