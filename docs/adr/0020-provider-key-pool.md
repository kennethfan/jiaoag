# 单 provider 多 key：轮询与冷却剔除

一个 provider 往往能拿到多把 key：同一个网关的不同账号、团队分摊的额度、临时备用。v1 只认 `api_key`，额度耗尽或单 key 被限流时，整个供应商不可用。本文把「一组等价的 key」收进 provider 内部，不改变上层任务、审批或审计。

## 背景

多 key 不是多 provider，差别在于语义：它们共享模型、base_url、超时与配额，任何一把都能完成同一个请求，选择哪把是纯调度问题。放在配置层做「多个 provider 轮换」会把这种等价关系交给用户手工维护，也会让会话绑定的 provider 名变得含糊。

失败原因也不能一视同仁：鉴权失败是这把 key 坏了；额度不足是这把 key 这一段时间没额度；限流是暂时性的、通常还带 `Retry-After`。请求本身写错了（400、上下文超限）换 key 没有意义，必须原样报给调用方。

## 决策

1. **`providers[].api_keys` 是一组等价的 key，优先于 `api_key`。**
   元素写法与 `api_key` 相同（明文、`$ENV`、`file:path`），启动时全部解析；任一解析失败都报 `api_keys[i]`，不回显明文。两者都为空是配置错误。单 key 写法保持不变。

2. **按键构造适配器，keyed 层位于速率限制之内、重试之外。**
   组合为 `retry(timeout(rate(keyed(adapter))))`。只有一把 key 时 `keyed` 不出现，行为与 v1 完全一致。

3. **轮询选择，游标成功也前进。**
   每次请求从游标位置找第一把未冷却的 key，并把游标推到它之后。均匀分摊额度，不因为某把 key 一直成功就永远只用它。

4. **三类失败才换 key：鉴权、额度、限流。**
   - 401 / 403 → 冷却 30 分钟
   - 402 或响应体命中 `insufficient_quota` / `insufficient credits` / `credit balance is too low` / `exceeded your current quota` / `billing hard limit` → 冷却 10 分钟
   - 429 → 有 `Retry-After` 用 `Retry-After`，否则 1 分钟；冷却上限 1 小时
   其他错误（400、上下文超限、网络抖动）不换 key：前三者换 key 也不会变好，后者交给外层重试。

5. **流式只在开流前换 key。**
   已经向调用方吐出 chunk 后再换 key 会重放内容，造成重复输出。此时直接返回错误，由用户决定是否重试。

6. **冷却只存在进程内。**
   重启后从全可用开始；没有持久化，也不需要——坏 key 会在第一次失败时再次进入冷却。全部 key 都在冷却时，挑最早到期的一把提前试探，避免供应商被永久判死。

7. **rpm / tpm 仍按整个 provider 计。**
   配额是「这个供应商每分钟能打多少」，不是「每把 key 乘 N」。多 key 提高的是可用额度，本地限速不应随之放大。

8. **不新增表、事件或协议。**
   key 选择是进程内的传输细节，不进任务事件，也不进审计；供应商身份仍以配置里的 `name` 为准。

## 后果

- 一把 key 鉴权失败或额度耗尽时，后续请求自动落到其他 key，任务不会因单 key 失效而中断。
- 轮询会均匀消耗多把 key；如果某把 key 额度更小，它会更早进入冷却，属于预期行为。
- 全部 key 失效时的错误会说明「N 把 key 均失败」，保留最后一次的底层错误便于排查。
- 目前没有按 key 的日志或指标；要观察哪把 key 在冷却，只能从失败错误和供应商侧账单推断。

## 备选

- **配置层多 provider 轮换**：把等价关系外包给用户，会话绑定哪个 provider 变得含糊，否决。
- **按权重/成本路由**：需要给每把 key 标价与权重，当前没有成本模型，暂不做。
- **持久化冷却状态**：收益小，坏 key 的再次失败成本很低，且会引入跨进程一致性负担。
- **在 429 时无限重试同一把 key**：会拖住任务且继续撞限流，交给冷却 + 外层重试更稳。
