# ADR-0029：多令牌与只读权限

- 状态：已采纳（v2.17）
- 日期：2026-11-24
- 相关：ADR-0026（传输加密）

## 背景

v1 只有一个 `server.token`。它承担两个职责：证明「你有权连接」，以及隐含「你可以做任何事」。到了 v2，这两件事的边界差别变得明显：

- 观测入口（`jiaoag-events`、未来的监控、CI 导出）只需要读事件与审计，却被迫拿一把能提交任务、裁决审批的钥匙。
- 令牌泄漏只能靠重启服务端换掉，期间所有连接一起断。
- 日志里看不出「这条连接是谁」，排障时只能猜。

## 决策

1. **命名令牌**：`server.tokens[]`，每项 `name` / `value` / `read_only`。`name` 只进日志与配置，不进协议；用于排障时区分身份。
2. **兼容老写法**：`server.token` 继续有效，等价于名为 `default` 的可写令牌；两者可并存，`AllTokens()` 统一展开。
3. **权限在连接上定格**：握手时匹配到哪把令牌，这条连接就带着它的 `read_only` 属性。权限判定不按每条消息重查配置——重载不该悄悄改变已建立连接的授权范围。
4. **只读白名单式拦写**：消息循环里用 `isWriteCommand` 拦 `session.create/update`、`task.submit/cancel`、`approval.resolve`、`project.trust/revoke`，回 `forbidden`；读命令（订阅、回放、审计、模型 / MCP / 技能列表）照常。选白名单而不是黑名单，是因为新加的读命令不该被误挡，而新加的写命令漏判会显式暴露在代码注释和测试里。
5. **SIGHUP 只重载令牌**：`config.Load` → `TokensFromConfig` → `SetTokens` 整体替换。监听地址、TLS、配额仍需重启——混在一起会让「发个信号」变成不可预期的大动作。
6. **重载失败保留旧令牌**：YAML 写坏或集合为空时只记 Error。否则一次手滑的配置就能让服务端变成谁都连不上。
7. **空集合一律拒绝**：启动与重载都拒绝零令牌，理由同上。
8. **认证循环不短路**：多令牌逐个常数时间比较，命中后继续跑完，避免「第几个匹配」体现在耗时上。
9. **客户端自动选可写令牌**：`ClientToken()` 优先 `server.token`，否则第一个可写令牌；只有只读令牌时客户端配置校验失败并给出可操作错误。`-token` flag 仍可覆盖。

## 后果

- 吊销是「改配置 + HUP」，不是管理接口；没有 API 能在线增删令牌。单用户工具的体量下这是有意的克制。
- 已建立连接不会被 HUP 踢掉。要立即断开就重启服务端。
- 没有 per-token 速率限制、过期时间或审计归属之外的配额。
- 只读令牌能看到所有会话的事件与审计：它是观测者，不是受限用户。
- Windows 无 SIGHUP，换令牌需重启。

## 备选

- **每令牌 scope 列表**（read/write/approve 分开）：现在只有两档，`approval.resolve` 单独授权暂时没有真实需求，多一维配置只是负担。
- **令牌存数据库 + 管理命令**：能在线上增删，但要引入「谁能管令牌」这个新权限问题，并且令牌属于部署配置而非运行数据。
- **JWT / mTLS**：真正的多主体认证，成本高一个量级；单用户工具先不做。
- **定时重读配置**：不用信号，但「什么时候生效」变得不可预期；HUP 是显式的。
