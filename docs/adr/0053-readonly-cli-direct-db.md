# ADR-0053：只读 CLI 直接读数据库

- 状态：已采纳（v2.51）
- 日期：2026-11-26

## 背景

`jiaoag sessions` 与 `jiaoag events` 原本都走 WS：先探测/拉起 `jiaoag serve`，再握手、拿令牌、订阅。
但它们只读，而且这个项目所有状态本来就落在一个 SQLite 库里。为了看 10 行会话列表去启动一个服务端，
既慢又容易误伤（自动拉起的 serve 会接手排队任务、占用端口、需要令牌文件）。

更根本的问题是：**只读命令不该依赖写路径的可用性**。服务端没起、令牌丢了、端口被占用，都不该让人
看不到自己的历史。

## 决策

1. **只读命令永远直连，不探测服务端**。`sessions list` 与 `events`（不带 `-url`）直接用 `mode=ro` 打开
   配置里的 `storage.db_path`；只有显式给 `-url`（或 `sessions rename/rm` 这类写操作）才走 WS。
2. **只读打开不建库、不跑迁移**。库不存在、是空文件、`schema_migrations` 不存在或版本低于当前程序，
   都直接报错并提示「先启动一次 jiaoag」，不做半吊子的自动修复。
   - 理由：迁移是写操作，而且多个运行时并发迁移刚出过竞态（ADR-0049 后的修复）。让只读命令去改库，
     等于把「看一眼」变成「升级我的数据」。
   - 版本高于当前程序也报错（升级了程序再读旧库是安全的，反过来不是）。
   - 打开后仍校验迁移 checksum 与关键表结构，损坏的库不会静默输出空结果。
3. **`events` 直连时用 250ms 轮询实现实时**。每轮 `Replay(session, lastSeq, 500)` 拉新事件、
   `ListAudit(cursor, 200)` 拉审计，按 `seq` / `id` 推进游标。与跨运行时事件补拉是同一语义与同一节奏
   （ADR-0051），不会出现两套不一致的「实时」。
4. **写操作保持现状**：`sessions rename/rm` 仍走 WS，本地没有服务端时照旧自动拉起。写要靠运行时的
   内存状态（事件广播、审计），直连 SQLite 写会绕开这些。
5. **`-db` 可以覆盖库路径**，用于备份副本、异地数据目录。
6. **不做静默降级**：直连失败不会退回去拉起服务端。要么按提示启动一次 `jiaoag`，要么显式给 `-url`。

## 后果

- 看历史不需要服务端、不需要令牌，毫秒级返回。
- 只读命令读到的可能比运行中的服务端晚最多 250ms（轮询间隔）；对导出与巡检无所谓。
- 库结构落后时命令直接失败，而不是自动迁移——这是刻意的取舍，升级动作只发生在启动时。
- 只读命令无法看到「还没落库」的内存状态（例如正在流式输出的 delta）；这与跨运行时订阅的限制一致。
- `sessions list` 的工作区过滤在客户端做（`Abs` + `EvalSymlinks` 归一），因为库里的 `workspace` 可能存的是
  软链路径（macOS 的 `/tmp` → `/private/tmp`）。

## 备选

- **保持全部走 WS**：部署简单、只有一条路径；代价是只读命令依赖服务端与令牌，且会自动拉起 serve。
- **直连也自动建库/迁移**：用户少一步；代价是只读命令变成写命令，多运行时下迁移竞态风险回来了。
- **用 `immutable=1` 打开**：更快；但 WAL 模式下会读到不一致的快照，且看不到正在写入的数据。
- **给只读命令单独的 Unix socket**：省掉 TCP 与 token；但引入第二种传输，且服务端没起时依然不可用。
