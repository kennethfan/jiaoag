# hunk 级部分批准：一次提案可以只应用部分块

一次改动 500 行的文件里只动了 3 行，现有审批粒度是「整份内容」。用户只有两个选择：接受全部，或者拒绝后让模型重来——而模型重来时往往给出同一份 diff。审批本该回答「这部分我要，那部分我不要」，粒度粗到没法表达，用户就会养成无脑按 `y` 的习惯，等于审批失效。

把一个提案拆成多次调用也不对：模型无法预知用户会挑哪几块，拆早了产生的中间态可能根本编译不过；拆晚了用户还是得逐个点。

## Decision

- **`approval.resolve` 增加可选 `hunks: [int]`**（0 起下标，指 `patch.ParseHunks` 解析出的块序号）。省略或全选 = 整份应用，走原来的写入路径；只给部分下标 = 只落这些块。显式 `[]`（非 nil 空切片）按参数错误处理，避免「传了空数组」被误解成「全选」。
- **部分应用在服务端重算，不信客户端拼好的内容**：`agent.applyChange` 先用 `workspace.Snapshot` 读当前文件，`patch.ApplyHunks(旧内容, change.Diff, 选中的块)` 逐块重放，按原文件换行风格 `Normalize`，重新算 `NewHash` 再 `Workspace.Write`。客户端只表达「要哪几块」，不发送内容。
- **CAS 不变**：仍以 `BaseHash` 比对磁盘。审阅期间文件被别处改了，提案照样 `stale`，不会拿旧基线拼出一份混合内容。
- **块级校验在重放时做**：context 行与 `-` 行必须与磁盘旧内容逐行一致，不一致报「旧内容第 N 行对不上（文件已变化）」。这让「diff 被截断」与「基线漂移」都在写入前暴露，而不是写出半份文件。
- **`allow_session` 与 `hunks` 同时出现时降级为 `allow_once`**：部分批准不建立会话白名单。白名单的键是 `工具+参数`，而它放行的是「整份写入」，与「这次只写第二块」不是同一个决定。
- **未选中的块要告诉模型**：`tool.result` 明确列出已应用 / 未应用的块号，并说明「那部分改动不在磁盘上，需要请重新读文件后再提出」。不说明的话，模型会以为改动已全部落盘，下一轮还在旧假设上继续。
- **留痕**：`proposal.applied` 带 `hunks` / `total_hunks`（整份写入时省略）；`write.applied` 审计的 detail 增加 `hunks` / `total_hunks` / `partial`。「谁批准了哪个文件的哪几块」因此可以只靠审计回答。
- **TUI 用独立选择模式**：diff 有两个以上块时提示 `[v] 逐块`；进入后 `space` 只改勾选、`y` 才提交，`esc` 回到全量视图。普通模式的 `y/a/n` 语义完全不变——逐块是附加能力，不是替换。

## Consequences

- 语义边界：一次工具调用仍然只有一次审批，部分批准不产生「稍后再批剩下几块」的挂起状态；未应用的块永久丢弃，除非模型重新提案。
- 部分写入后的文件内容可能不满足模型原本的意图（比如只应用了 import 那半、没应用函数体），这属于用户的选择，工具结果会如实说明哪些块没写。
- `patch.ApplyHunks` 是纯函数，块解析失败、越界下标、上下文不匹配都不会走到 `Workspace.Write`；但合并结果本身不做编译校验——那是测试与 `diagnostics` 的事。
- 新增协议字段与两个事件字段都是可选的，旧客户端不传 `hunks` 时行为与之前完全一致。

## Considered Options

- **让模型自己拆成多次 `write_file`**：模型无法预知用户会选哪几块，且每次调用都要单独审批，交互次数反而更多。
- **客户端拼好内容再提交（`content` 字段）**：服务端就无法证明落盘内容与用户看到的 diff 一致，也绕过了 CAS 的基线语义。
- **把未选中的块记成「待审批」留到下一轮**：需要新的挂起状态与过期策略，而用户真正的意愿通常是「这段不要了」。
- **在 TUI 里做行级勾选**：行级选择会切碎上下文行，产生的中间文件几乎必然不可用；块（hunk）是 diff 自带的最小自洽单位。
