# 0041. Web 前端：原生页面，go:embed，复用同一套协议

状态：已采纳（v2.39）

## 背景

TUI 是唯一的客户端。它要求终端、要求键盘，长任务跑到一半想看进度或者批一个 diff，就得回到那台机器上。服务端已经是「协议 + WS + 事件日志」的形态，第二个客户端本来就不该需要新协议。

问题只有三个：页面怎么来、范围多大、怎么鉴权。

## 决策

1. **原生 HTML + CSS + ES module，用 `go:embed` 打进二进制**。不引 node、打包器、前端框架。理由：这个项目的分发形态是「一个 bin/jiaoag」，多一个 `npm install` 就多一类不能离线复现的构建；页面复杂度也不值得。
2. **同端口同源，挂在 `/`**。不另开端口、不设 CORS：页面与 `/ws` 同源，浏览器的同源策略帮我们兜住一部分问题，反代也只需要一条规则。
3. **静态资源公开，数据必须带令牌**。`/`、`/app.css`、`/*.js` 匿名可读（它们不含秘密，且 `<script src>`/`<link href>` 无法附加自定义头）；`GET /api/info` 与 `/ws` 都走与 TUI 完全相同的 Bearer 校验。
4. **`/ws` 额外接受 `?token=`**。浏览器的 `WebSocket` 构造函数设不了请求头，这是唯一可行形态。代价是令牌可能落进代理访问日志——在 `docs/web.md` 里写明远端必须配 TLS 并裁剪日志查询串。
5. **页面首次粘贴令牌，存 `localStorage`**。不做登录页、不做服务端会话：令牌就是凭据，和 TUI 的 `-token` 等价。
6. **范围对齐 TUI，唯一例外是 `!` 本机命令**。浏览器里不存在「安全地起一个本机 shell」，而 agent 的 `run_command` 已经覆盖了执行需求（审批、审计、执行后端、资源限制都在）。少这一个功能比伪造一个更安全。
7. **事件驱动重建，不引入新的服务端状态**。页面刷新或断线重连后按 `lastSeq` 增量续传、`from_seq=0` 全量重放，和 TUI 一致；服务端没有为 Web 增加任何帧类型。
8. **协议常量在页面上集中一份，并有测试对齐**。`assets/protocol.js` 抄一份类型/事件/状态名，`internal/webui/webui_test.go` 从 `internal/protocol` 与 `internal/domain` 抽真实常量比对——防止服务端改名后页面静默失效。

## 后果

- 页面能力受浏览器限制：不能起本机命令，不能读本地文件，长 diff 只能靠滚动。
- 没有构建步骤意味着没有 tree-shaking、没有 TypeScript 类型检查；代价用「集中常量 + 服务端常量比对测试」部分弥补。
- 前端代码进了 Go 二进制（约几百 KB 的文本资源），不影响启动，但改页面需要重新 `make build`。
- 令牌存 `localStorage` 意味着同一台机器的其他页面脚本（若有 XSS）可以读它。当前页面不渲染任何用户可控的 HTML（对话内容一律 `textContent`），风险可控，但这仍是「浏览器里的凭据」的固有代价。
- 页面不实现「多窗口共享状态」，两个浏览器窗口各自持有一条 WS 连接，各自重放。

## 备选方案

- **React/Vue + 打包**：开发体验更好，但引入 node 工具链与产物提交问题，与「单二进制、可离线构建」冲突。
- **独立子命令 `jiaoag web` 起另一个端口**：多一个要配 TLS、要多一条反代规则；同源挂载在 `/` 更省。
- **服务端渲染 + 表单 POST**：无法承载流式输出与事件回放，等于把协议重做一遍。
- **把令牌写进页面或 cookie**：会让「谁能拿到页面」变成「谁能拿到令牌」，且 cookie 要处理 CSRF；粘贴 + `localStorage` 更直白。
- **Web 端不复用 `?token=`，改用一次性 ticket 换 cookie**：更严谨，但需要服务端新增签发/校验逻辑与过期回收，首版收益不足。
