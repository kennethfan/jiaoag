# ADR-0035：Webhook 通知

- 状态：已采纳（v2.23）
- 日期：2026-11-24
- 相关：ADR-0013（审批走事件）、ADR-0027（只读事件导出）、ADR-0029（只读令牌）

## 背景

审批与任务结果此前只能从 TUI 看，人离开电脑后完全不知道有任务在等。
「事件导出」解决的是事后取证与观测，不解决「现在有人需要你」这件事。

可选的现成通道有：邮件、IM（飞书/钉钉/Slack）、自建 HTTP 端点。
判定标准是：宿主侧不该绑定任何一个 IM 的鉴权细节，也不该为了发一条通知
引入新的依赖或后台任务。HTTP POST + 可选的 HMAC 签名足够覆盖全部这些场景
（各 IM 都有自己的转发器或机器人 webhook）。

## 决策

1. **只推两类事件**：`approval.requested`（有人要裁决）与任务终态
   （`completed` / `failed` / `canceled`）。队列、轮次、工具结果这些看一眼 TUI
   就够，推出去只是噪音，还会把 webhook 变成第二条事件流。
2. **载荷是自足的小对象**：事件名、类别、时间、会话/任务 id、状态、工具名、
   审批 id、提示词前 120 字。不含 diff、argv、工具输出——这些可能很长，
   也可能含敏感内容；需要细节就回 TUI 或导出事件。
3. **异步、有界、可丢**：`commit` 落库并广播后调用 `Notify`，实现必须是非阻塞的
   （`Dispatcher` 内部 256 的队列）。队列满即丢并记 warn：通知是旁路能力，
   不能反压任务执行。
4. **失败重试 3 次**：5xx、429、网络错误按 1 次 500ms 递增退避；4xx 不重试
   （配置或契约问题，重试没有意义）。重试在后台进行，不占任务的时间。
5. **可选 HMAC-SHA256 签名**：配了 `secret` 就在请求头带
   `X-Jiaoag-Signature: sha256=<hex>`，接收方用同一 secret 复算校验。
   不配也能用，但接收方无法区分请求是否来自本机。
6. **配置即全部**：`notify.webhooks[]`（name/url/secret/events/timeout_s/enabled），
   URL 只接受 http/https，事件名白名单校验，名字可重复检查。没有单独的
   「发送测试」命令——直接跑一个任务或等一次审批就是最真实的测试。
7. **不写数据库、不发事件**：投递结果只进进程日志。通知成功与否不属于
   任务事实，不该污染事件日志。

## 后果

- 人不在电脑前时，手机上的 IM 机器人能收到「任务 X 在等审批」并带上下文。
- 通知与任务解耦：webhook 挂掉、变慢、返回 500 都不影响任务完成。
- 提示词摘要会离开本机（发往用户自己配置的端点）；需要更严格时可以只订阅
  `failed`，或在接收端做脱敏。
- 没有去重与「已读」语义：同一次审批在重连、重放时不会重复推（只在写库时
  触发一次），但网络重试可能造成接收端重复收到同一条。
- 没有全局开关之外的分级：想静音就 `enabled: false` 或直接删配置。

## 备选方案

- **邮件**：需要 SMTP 凭据与退信处理，且多数邮箱对机器发信有限制。
- **直接集成 IM SDK**：绑定具体厂商、引入依赖，且每个厂商的鉴权都要维护。
- **复用事件导出 + 外部消费者**：通用但需要常驻进程，正是 `jiaoag-events`
  的定位；通知是「推」而不是「拉」，不该要求用户自己跑一个消费者。
- **在服务端做通知模板**：模板语言会成为第二套需要维护的配置面，
  接收端本来就能自由渲染 JSON。
