# ADR-0038：shell 命令作为一等入口

- 状态：已采纳（v2.27）
- 日期：2026-11-24

## 背景

`run_command` 从 v1 起只接受 argv（`{"argv": ["go", "test", "./..."]}`），执行时逐 token 传 `exec`，不经过 shell。ADRs 0004 据此设计了两道判定：argv 里出现 shell 元字符（`| & ; < > $ \` ( ) * ? [ ] ~`）就要求审批，否则按程序名匹配命令白名单。

问题出在「模型真正想做的事」和这套接口不匹配：管道、重定向、通配符、多条命令、变量展开都得有 shell。模型于是自己包一层 `["sh", "-c", "整条命令"]`。这在语义上完全可行——`sh` 是个普通程序，argv 形式也允许——但代价是三重的：

1. **策略理由变成误导**。命令里带 `|` 时命中 `metachar`，报「argv 含 shell 元字符 "|"」；不带元字符时命中 `not_whitelisted`，报「sh 不在白名单内」。两句读起来都像工具出错，实际都是「shell 没法静态判定」。
2. **审批面板失去可读性**。一条命令被拆成 `argv[0] sh` / `argv[1] -c` / `argv[2] 整条`，最需要读的正文被推到第三行，还经常折行。
3. **能力被藏起来**。schema 里明写「不要传 shell 字符串」，模型只能违反提示词去用 shell，或者放弃任务。

也就是说：shell 是刚需，但接口把它当例外。

## 决策

### 1. 新增 `shell` 字段，与 `argv` 二选一

```json
{"shell": "go test ./... 2>&1 | tail -20"}
```

`Prepare` 把整条命令包成 `[sh, -c, <text>]`（Windows 上是 `[cmd, /c, <text>]`），同时把原文放进 `tools.Command.Shell`。

- 同时给 `argv` 与 `shell`：参数错误。一条命令要么能拆成 argv（可静态判定），要么整体交给 shell（一定审批）；两者并存会让「到底跑了什么」含糊。
- `shell` 去空白后为空：参数错误。
- 长度上限 8 KB（`maxShellBytes`），拒绝 NUL。整条命令不按 token 校验——`maxTokenBytes`（4 KB）是给单个 argv 元素的，一条带内联脚本的命令很容易超过它。

### 2. 平台 shell 固定，不跟随 `$SHELL`

Unix 用 `sh -c`，Windows 用 `cmd /c`。审批面板展示的是这条命令本身，执行器必须与审批时看到的语义一致；跟随用户的 `$SHELL` 会让「我批的是这条命令」变成「我批的是这条命令在你那个 shell 里的解释」。

### 3. 策略层：shell 命令固定要人看，且先于元字符判定

`Ruleset.Evaluate` 在 `metachar` 检查之前拦下 `cmd.Shell != ""`：

```
shell: 需要 shell 解释（管道/重定向/多命令），无法静态判定
```

理由有三：元字符对 shell 是正常语法，不是注入；`argv[0]` 永远是 `sh`/`cmd`，白名单按程序名匹配必然落空；而 shell 命令的实际行为无法从 token 序列推出（`go test; rm -rf /` 与 `go test` 的首 token 相同）。

**shell 命令不享受白名单自动放行，也不因为 `trust`/`allow` 类配置而免审。** 这是刻意的：能静态判断的用 argv（可自动放行），不能判断的用 shell（一定审批）——把两者分开，比让模型偷偷包一层、再靠元字符偶然撞上审批要诚实。

### 4. 审批、事件、审计都带 shell 标记

- `approval.requested` 增加 `shell`（整条命令原文）；客户端应把它当作主体展示，不要再拆 `command` 三段。
- TUI 命令审批面板：`shell` 非空时显示 `shell  <整条命令>` + cwd / backend / timeout / 判定，不再列 `argv[i]`；对话区提示行同样显示整条命令。
- `exec.*` 审计的 detail 增加 `"shell": true`，`argv` 仍是 `[sh,-c,<整条>]`——审计要能回答「这条到底怎么执行的」，所以保留真实 argv，同时用一个布尔位标明这是 shell 形态，便于统计与检索。

### 5. 兼容旧形态

模型仍可能写 `["sh", "-c", "..."]`（旧提示词、旧会话回放）。这种调用按普通 argv 处理：`Shell` 为空，会命中 `not_whitelisted: sh 不在白名单内`，依旧需要审批。不做「自动识别 argv 形状并改写成 shell 形态」——那会让策略判定依赖字符串猜测，且历史事件的语义会被改变。

## 后果

- 模型有了正当的 shell 入口，不必再违反 schema 提示；「需要 shell 特性」从潜规则变成显式选择。
- 审批面板读起来是「一条命令」，而不是「一个叫 sh 的程序带了两个参数」。
- 策略理由从 `metachar` / `not_whitelisted` 变成 `shell:`，用户不会再误以为工具出了 bug。
- 审计多一个布尔位，能统计「多少命令必须人看是因为走了 shell」。
- Windows 上 `cmd /c` 的引号与变量展开规则和 `sh` 不同：同一段命令在两个平台上可能不等价。这是平台现实，文档写明，不做语法翻译。
- 不做「shell 命令的静态解析」（拆出首个命令再匹配白名单）：`/bin/sh` 的语法足够复杂，任何自制解析器都会给出假阴性，而假阴性的代价是自动放行了一条人没看过的命令。

## 备选方案

- **保持现状，只写文档**：模型继续包 `sh -c`，理由继续误导，面板继续拆三段。成本为零，问题依旧。
- **只改展示**：识别 `argv[0]∈{sh,bash}` 且 `argv[1]=="-c"` 后归一显示。能解决可读性，但策略理由仍是 `metachar`，且模型还得继续违反提示词。
- **让 `run_command` 接受一个字符串并总是交给 shell**：最省事，但会丢掉「可静态判定、可自动放行」的整类命令，等于把 M5 的白名单废掉。
- **在 shell 文本上做命令解析再匹配白名单**：见上，假阴性风险不可接受。
