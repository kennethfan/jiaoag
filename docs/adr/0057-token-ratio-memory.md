# ADR-0057：上下文估算系数跨任务记忆

## 背景

上下文预算按「估算 token」算（ADR-0031）：按字符类别加权，再用每轮供应商回报的
`prompt_tokens` 做在线校准，系数是「实际/估算」的 EWMA，夹在 `[0.5, 3]`。

问题是这个系数**只活在一个任务里**：`tokenEstimator` 在 `Run` 开头创建，任务结束
就丢。后果是每个新任务的第一二轮都从 `1.0` 冷启动，而中文与代码的偏差最大可以到
3 倍——冷启动期间预算算得过松或过紧，压缩触发点跟着偏。第三轮起系数基本收敛，
但任务常常只有三五轮，冷启动占了相当比例。

## 决策

1. **把系数按 `provider/model` 落库**（`token_ratios` 表，迁移 0011），任务结束时
   回写。键带 model 的理由：换模型后旧系数没有参考价值，同一供应商内不同模型的
   分词器差异可能比跨供应商还大。
2. **只在有样本时回写**。一次任务如果所有请求都低于 `minCalibrationTokens`（200），
   系数没被任何真实用量修正过，此时回写等于用默认值覆盖历史——`calibrated()` 拦住
   这种情况。
3. **读失败与写失败都不影响任务**。读失败按默认值起算（记 `Warn`），写失败只记
   `Warn`：预算精度是体验问题，不是正确性问题。
4. **读入时校验范围**。落库值可能是旧版本或手工改坏的，越界（`< 0.5` 或 `> 3`）
   一律当作没有历史，退回 `1.0`。
5. **计数 `samples` 只做观测**。排查「这个系数是一次猜的还是几十次校准出来的」时
   有用；判断是否需要重新校准不依赖它。
6. **并发写取后写者**。同一 `provider/model` 上两个任务同时结束会互相覆盖，但系数
   本身是 EWMA 的近似值，谁最后落库不影响正确性；用 UPSERT 而不是读-改-写，避免
   多运行时之间丢更新。

## 后果

- 新任务首轮就用上历史系数，中文/代码类项目的预算偏差明显变小。
- 多了一张 12 张表之外的小表，以及一次任务提交时的读 + 任务结束时的一次写——量级
  可以忽略。
- 换供应商或换模型后前几个任务仍会冷启动（键不同，不会误用旧值）。
- 系数是「最近若干次的指数平均」，模型或提示词大改后需要几次任务才能重新收敛；
  想立刻清掉可以 `DELETE FROM token_ratios WHERE key = '...'`。
- 估算器仍然不是分词器：它只是让偏差更快收敛，不能替代按内容配预算的判断。

## 备选

- **按 provider 分键**：键更少，但同一供应商内混用大小模型时会串。
- **落文件**（`~/.local/share/jiaoag/calibration.json`）：不进迁移，但多一处与库
  不一致的状态，`VACUUM INTO` 备份时也不会带上。
- **全局一个系数**：实现最省，但不同供应商偏差方向可能相反，互相拖。
- **不改**：冷启动只在每个任务前两轮，影响有限——但这是「白拿的精度」，成本只有
  一次查库与一次 UPSERT。
