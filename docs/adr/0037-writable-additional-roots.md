# ADR-0037：附加根可写、命令按根执行

- 状态：已采纳（v2.25）
- 相关：ADR-0036（只读附加根）、ADR-0011（可插执行后端）、ADR-0015（sandbox）

## 背景

v2.24 的附加根只能读。实际使用里最常见的两个诉求反而是写与跑：

- 改共享库里的一个函数，然后回到主仓升版本；
- 在多仓工作流里，对每个仓分别跑 `go test ./...`。

只读附加根能「看见」问题，却没法完成修复，用户仍然要开两个会话、复制粘贴改动。

## 决策

1. **附加根可写**：`write_file` / `edit_file` 接受 `alias:path`。写入链路不变——`Prepare` 只产出
   `Change`，审批通过后由 agent 落盘；变的只是「落到哪个工作区」。
2. **`Change` 带根**：新增 `Root`（别名）与 `Rel`（根内相对路径）。`Path` 保留为展示用的
   `alias:rel`，事件、diff、审计都用它。CAS 与落盘用 `Root`+`Rel`，不解析展示字符串。
3. **命令按根执行**：`run_command` / `check_command` 增加可选 `root` 参数。`cwd` 切到该根，
   权限引擎的 `path_args` 判定也跟着切——「参数必须落在 cwd 内」本来就以命令自己的 cwd 为边界。
4. **沙箱可写范围**：`exec.Command` 新增 `Writable []string`（宿主注入，模型不可指定）。
   sandbox 后端把它并进可写白名单；direct 后端不读（它本来不隔离）。
   敏感目录的 deny 判定改为对照全部可写根，避免「会话根恰好落在 `~/.config` 下」被误禁。
5. **审计带根**：`write.applied` 的 detail 增加 `root`；命令审计增加 `root`。主根仍为空字符串，
   所以既有的 SQL 与导出不受影响。
6. **项目级扩展仍只读主根**：多份 `AGENTS.md` / `.jiaoag` 的注入顺序与优先级没有共识，
   宁可不做也不做半套。
7. **TUI 不引入「当前根」**：没有隐式状态，写路径用 `alias:`、命令用 `root`，
   模型与人都看得到自己选了哪个根。
8. **`extensions_digest` 不变**：挂载哪些根仍不计入任务指纹；换根不等于换策略。

## 后果

- 一次任务可以同时改多个仓，diff 面板与审计能指出改的是哪个仓。
- 多根写入的 CAS 仍按单文件比较：两个会话同时改同一个文件，后写者照旧拿到 `stale_proposal`。
- 沙箱下命令的可写面变大（所有会话根），这是「在 lib 里跑构建」的必然代价；
  不想要就用 `-root` 只挂需要的那一个。
- `run_command root=lib` 与 `path_args` 的耦合意味着：附加根里跑的 `go test` 不会因为
  模块缓存目录不在根内被拒——缓存目录本来就在可写白名单里。

## 备选

- **只开放写入、不放命令**：能改不能测，验证闭环断掉一半。
- **所有根完全等价（含 git 工具、项目扩展）**：改动面扩散到工具、提示、沙箱三处，
  且没有真实需求驱动；留作后续 issue。
- **在宿主侧引入「当前根」会话状态**：省几次参数，但让审批与审计的路径含义依赖隐式状态，
  回放时容易对不上。
