# 跨会话项目记忆：MEMORY.md + remember 工具

每个任务都从会话事件重建上下文，跨会话则从零开始。用户反复交代的项目约定（构建命令、目录结构、踩过的坑）只能每次重说。本文落下最小形态的长期记忆：工作区根目录的 `MEMORY.md`，加一个只能追加、必须过 diff 审批的 `remember` 工具。

## 背景

长期记忆有三条常见路线：

- **数据库 + 检索**：把事实存表，按相似度召回。需要索引、排序、失效策略，还要解释「为什么这条被召回」。
- **向量库**：召回质量取决于 embedding 与切块，运维成本最高，单用户本地场景收益不明。
- **工作区文件**：人可读、可编辑、可版本控制，天然按仓库隔离；缺点是每轮都要付全文的 token。

单用户编码 agent 的项目事实通常只有几十条，全文注入完全放得下。先做文件，等真的装不下再谈检索——这是可逆的起点，不是终局。

## 决策

1. **记忆就是工作区根目录的 `MEMORY.md`，整份注入。**
   注入为一层提示词，排在内置核心之后：它提供项目事实，不能覆盖安全边界、工具协议与审批规则。文件不存在是正常状态，不报错、不产生提示层。

2. **放在根目录，不建 `.jiaoag/` 子目录。**
   落盘走 `workspace.Write`，它要求父目录已存在。为一个文件隐式建目录，会让「路径写错」变成「在奇怪的地方建目录」。根目录文件也让用户一眼看得到、随手能改。

3. **写入只有一个入口：`remember` 工具，走 diff 审批。**
   工具实现 `EffectProposeWrite`：`Prepare` 只产出 `Change`（新内容、diff、新旧 hash），`Execute` 不落盘。用户批准后由宿主做 CAS 与原子写。模型不能整文件覆盖，只能追加一条格式化后的记忆；重复内容直接拒绝。

4. **上限是硬约束：单条 500 字，全文 8 KB。**
   记忆是每轮都要付的上下文成本，必须有界。追加会超过 8 KB 时拒绝，并提示先删除或精简旧条目；加载超过 8 KB 时只取前 8 KB（按 rune 边界回退），并在正文末尾附提示。单条格式为 `- YYYY-MM-DD: 事实`，换行压成空格，避免破坏条目结构。

5. **按工作区隔离，不做全局记忆。**
   同一台机器上的两个仓库互不可见。记忆不记密钥、口令、个人隐私；文件可以被 `.gitignore`，是否提交由用户决定。

6. **记忆进入提示词哈希，随任务冻结。**
   `MEMORY.md` 参与 `prompt.Assemble` 的哈希，因此改变记忆会改变 `system.Hash` 与 `extensions_digest`。会话进行中改文件不影响在跑任务，下一个任务才生效——与项目提示词的处理一致。

7. **默认开启，可整体关闭。**
   `agent.memory: auto`（默认）注入记忆并注册 `remember`；`off` 既不注入也不提供写入工具。关闭后 `MEMORY.md` 原样保留，重新开启即可恢复。

8. **不新增表、事件或协议。**
   记忆是文件，不是会话事实：不写 `compactions` 之类的缓存表，也不产生专用事件。写入沿用现有的 `approval.requested` / `proposal.applied` 链路，审计与 TUI 审批面板自动覆盖。

## 后果

- 每个任务多付最多 8 KB 的提示词；项目事实越多，固定成本越高。
- 修改记忆会让提示词哈希变化，可能影响供应商侧的前缀缓存命中；这是「记忆即时生效」的代价。
- 没有语义检索：模型看到全部记忆，相关性由自己判断。条目需要用户与模型共同维护，否则会退化成杂物间。
- 人工直接编辑 `MEMORY.md` 绕过审批。这是刻意保留的逃生口：工作区文件本来就在用户控制下，审批约束的是模型，不是用户。
- 记忆内容可能包含误导性指令。它排在内置核心之后，且用户能看到每次 diff，但不能防止用户自己写入恶意内容——信任边界仍是工作区。

## 备选方案

- **数据库 + 检索**：需要召回策略与失效机制，单用户几十条事实不值。
- **向量库**：多一层依赖与运维，且「为什么召回这条」难以解释。
- **会话摘要复用**：摘要描述的是任务进度，不是项目事实；混在一起会让两者都变模糊。
- **直接复用 `AGENTS.md`**：项目指令与 agent 记忆语义不同（前者约束行为，后者补充事实），混写会让人分不清哪条必须遵守。
