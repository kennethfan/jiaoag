# ADR-0040：同窗口多会话（标签页）

状态：已采纳（v2.38）

## 背景

一个 TUI 窗口原本只对应一条会话：`/sessions` 面板里 `enter` 会退订旧会话、清空视图、再订阅新会话；而且目标会话**有未结束任务时直接拒绝切换**。

结果是「并行」这件事在界面上做不到：后台那条任务还在跑，你看不见它的进展，也切不过去——只能等它结束。服务端其实早就支持一条连接上按会话 id 维护多条订阅（`clientConn.subs` 是按会话分键的 map），事件信封里也带 `session_id`，所以限制纯在 TUI 这一侧。

## 决策

1. **一个窗口多标签，每条标签一个会话。** `/sessions` 里 `enter` 把会话开成标签（不再因为它在跑任务而拒绝），`ctrl+n` / `ctrl+p` 循环，`ctrl+w` 关当前标签（至少留一个）。

2. **标签只存徽标，不存正文。** 每条标签只记 `title / status / pending / unread / provider / model`。对话历史不复制第二份：切过去时发 `event.subscribe from_seq=0` 全量回放，对话、工具调用、待审批面板都靠事件重建。这样标签状态的内存占用与事件流长度无关，也不会出现「两份状态谁是对的」。

3. **背景会话保持订阅，但只更新徽标。** 事件按 `env.SessionID` 路由：不是当前会话就交给 `noteBackgroundEvent`，只改 `status / pending / unread`，不碰对话区——否则两条流会插在一起，读起来是乱的。

4. **普通切换不退订。** 只有关标签（`ctrl+w`）才退订。退订会停掉后台任务的进度徽标，那就失去了多开的意义。

5. **标记按「需要你动手」排序**：`!`（有未裁决审批）> `●`（运行中）> `◌`（排队）> `✖`（失败）> `·N`（未读条数）。审批只有人能推进，所以它压过一切状态。

6. **关标签不删会话，也不打断任务。** 任务在服务端跑，关标签只是关掉视窗；重新打开会从事件重放恢复。真要清除用 `/sessions` 的 `d` 或 `jiaoag sessions rm`，那走的是删除会话的既有路径（忙会话拒绝）。

7. **标签行只在两个以上会话时出现。** 单会话时界面布局与以前完全一致，不额外占一行；固定底部区的高度由 `len(dock)` 现算，所以多一行不会挤掉内容区。

8. **启动即恢复：本目录的会话全部开成标签，接到最近更新的那条上。** 原来的行为是每次启动都新建会话（`-c` 才继续最近一条），结果是同一个目录攒下一堆看不见的孤儿会话——它们还在库里、还有任务，但界面上完全没有入口。恢复全部是「会话属于工作区」这个模型的自然结论：一个目录的历史就该在那里可见。没有会话时才新建，想另开一条用 `/new`。`-c` 因此删掉（它已经成了默认行为）。

9. **标签行放不下时以当前标签为中心开窗**，两端用 `…` 与 `+N` 标出还有多少条。恢复全部意味着一个目录可能有十几条历史，全挤在一行会被截断成看不出结构的一串；当前标签永远可见是底线。

10. **关闭当前标签时先清 `sessionID` 再激活邻居。** `activateTab` 会把「当前会话」登记进标签表，先清空才不会把刚关掉的那条又登记回来（实现时踩到，已由测试固定）。

## 后果

- 切换有回放开销：会话越长，切过去越慢（与 `-s` 重连同一个代价）。标签里不缓存正文是刻意的取舍。
- 后台会话的未读计数只统计 `assistant.message` 与 `tool.result`；流式 delta 不计（每秒几十条会把徽标刷成噪音）。
- 标签行挤占一行高度：小终端（如 20 行）少一行内容。
- 启动即恢复意味着长时间使用后一个目录会攒下很多标签。清理靠 `/sessions` 的 `d` 或 `jiaoag sessions rm`，标签本身不自动裁剪。
- 不提供「新窗口」或真正的分屏：同屏看两条对话需要另一套布局（滚动、审批归属都要拆），不在本次范围。

## 备选

- **每条会话一份完整视图状态**：切换零延迟，但内存与状态同步成本翻倍，且要实现「后台流写入非当前视图」的合并逻辑，容易写出两套真相。
- **分屏并排**：同时可见，但布局、滚动、审批面板归属、输入焦点全要重做，工作量是标签的 3 倍以上。
- **每个会话开一个进程/窗口**：现在就能做（`jiaoag tui -s …` 各开一个），但要在多个终端窗口之间自己找，且每个窗口都会尝试复用/拉起服务端。标签是窗口内的等价物。
- **切换即退订、切回再订阅**：省一个订阅协程，但后台任务的状态就看不到了——与需求相反。
