# ADR-0048：契约与传输分离，TUI 在进程内持有运行时

状态：已采纳（v2.46）

## 背景

TUI 与服务端本来就在同一台机器上，但 TUI 只能通过 `ws://127.0.0.1:8788/ws` 连接：要端口、要令牌、要 TLS 配置，TUI 还得负责「连不上就拉起一个 `serve` 子进程」并处理它的生死。这带来三类问题：

1. **多一层没有收益的故障面**：端口占用、令牌文件读不到、子进程孤儿、TUI 退出后服务端还在跑。
2. **协议逻辑只能长在 server 里**：21 个命令 handler 平均 40 行，业务、回退 session id、只读校验、错误码、帧编码混在一起，Web 端要复用只能照抄。
3. **两个客户端就要两套实现**：TUI 走 WS，Web 也走 WS，但所有语义都在服务端代码里，没有可被进程内直接调用的接口。

同时，用户明确了一条边界：**不要 socket**。多客户端不是 TUI 的职责——需要多客户端时先起 `serve`。为了「TUI 先启动、之后还想接第二个客户端」而引入 Unix domain socket，只会把同一套生命周期问题换个地址再演一遍。

## 决策

1. **契约与传输分离**
   - 契约 = `internal/rpc`：`Service` 强类型接口（16 个方法）、`Principal`（令牌名 + 只读）、`Error{Code,Message}`、事件流的订阅语义。
   - 传输 = 薄适配器：WS（`internal/server/adapters.go`）只做「解码 → 填 session id → 调契约 → 编码/错误帧」；进程内（`internal/tui/local.go`）只做「按帧类型派发 → 调契约 → 构造回执帧」。
   - 一份契约，两种传输；新增传输不改业务。

2. **TUI 默认进程内**
   - 裸跑 `jiaoag`：`internal/boot.Open` 在本进程建 store/app/runtime，TUI 通过 `localTransport` 直接调 `rpc.Core` 与 `rpc.Streams`。
   - 无端口、无令牌、无 WS、不拉起子进程；`Model.conn` 从 `*websocket.Conn` 变成 `Transport` 接口。

3. **所有权靠文件锁**
   - 锁文件：`<db 所在目录>/runtime.lock`（flock 独占、非阻塞；Windows 用 `LockFileEx`）。
   - 拿不到锁时：若配置的 listen 可达 → 降级为 WS 客户端；不可达 → 报错退出，并说明「已有实例占用数据目录但没有监听」。
   - `jiaoag serve` 与内嵌 TUI 都先拿锁，因此不会出现两个运行时同时写同一个库。

4. **boot 成为唯一的装配入口**
   - `boot.Open` 负责配置加载与校验、规则集与 feed、执行后端、存储、app、MCP/插件/通知/后台进程表、`ConfigureRuntime`，最后暴露 `Core` 与 `Streams`。
   - `serve` 与内嵌 TUI 共用同一个 `Stack`，避免两套启动路径漂移。

5. **不做 UDS**
   - 「TUI 先起、后来想接第二个客户端」这个场景的答案是：退出 TUI，改起 `serve`。
   - 契约层已经把位置留好（`Transport` 与 `Service` 都不假设传输是网络），将来真需要再加适配器，不影响今天的所有者语义。

6. **退出要有确认**
   - 有运行中/等待审批的任务、排队任务、或后台进程时，第一次 `ctrl+c`/`/exit` 只提示，第二次才取消任务、停止后台进程并退出。

## 后果

- 单机日常使用少了一个端口、一份令牌依赖和一个子进程；`lsof -i` 上不会再有 TUI 的监听。
- Web 端与远程访问仍然走 `jiaoag serve` + WS，行为不变；TUI 在 serve 运行时自动降级成客户端，不需要用户选择。
- 同一数据目录一次只能有一个运行时：第二个 TUI 会被拒绝，这是刻意的取舍（两个运行时同时写 SQLite 的 WAL 才是真的灾难）。
- 只读 CLI（`jiaoag sessions list`、`jiaoag events`）目前仍会在连不上时拉起 `serve`；「直连 SQLite、不拿锁」作为后续优化保留在路线图里，不在本决策范围内。
- 事件流的两条路径共用 `rpc.Streams`（回放 → 快照 → 去重 → live），不存在「本地模式少一层回放」的偏差。

## 备选

- **保留 WS + 自动拉起**（改动最小）：不解决子进程生死、端口与令牌的额外故障面。
- **Unix domain socket**：多客户端问题表面上解决了，但生命周期、权限、跨平台（Windows）都要重做一遍；且用户已经明确不需要「TUI 先起再接入」。
- **契约层只抽接口、不搬实现**：server 仍持有业务，localTransport 只能复制一遍逻辑，等于两份实现。
- **TUI 内嵌同时监听端口**：回到「谁是所有者」的老问题，会出现两个合法入口写同一个库。

## 修订（v2.47）：不再用文件锁，多运行时靠占位与租约

原决策 3「所有权靠文件锁」已被 ADR-0049 取代。原因：SQLite 本身支持多进程并发写
（WAL + busy_timeout），锁真正要挡的不是「同时写库」，而是只存在于进程内存里的
运行时状态——任务队列、审批等待者、事件广播。把这些状态搬进数据库后，文件锁就
没有必要，第二个 TUI / `serve` 可以同时使用同一个数据目录。

- 调度：`tasks.owner` + `tasks.lease_until`，抢占是单条原子 UPDATE（ADR-0049）。
- 审批跨进程与事件 tail 仍在 P2/P3，未完成前不要把「两个运行时能同时跑任务」
  误解成「任意客户端都能看到另一个进程的实时流式输出」。
