# ADR-0052：后台进程面板与孤儿的处置

- 状态：已采纳（v2.50）
- 日期：2026-11-26

## 背景

后台进程（`run_command background=true`）落库后，句柄只属于启动它的运行时。属主崩溃时，这些进程会停在 `running`，没有任何运行时能再管理它们——`ProcTable` 里没有句柄，`stop_command` 只能写 `stop_requested`，而写进去也没人执行。

先前的做法是「标成 `orphaned` 只读展示」，但没有入口展示：用户只能在 SQL 里查。同时 `background_procs` 只存了 pid，不存命令行，即便列出来也认不出是哪一条。

## 决策

1. **`/ps` 列出全部后台进程**，不是只列当前会话。孤儿往往属于一个已经关闭的会话，按会话过滤等于看不到它们。排序：`orphaned` → `running` → `其他`，同组按启动时间倒序。

2. **编号要能认**：迁移 0010 给 `background_procs` 加 `argv`（JSON 数组），面板显示 `npm run dev` 这样的命令行，而不是只有一个 pid。

3. **两个动作分离，语义不同**：
   - `d`：**只删记录**。只允许非 `running`，因为它不碰进程，只是把已经没用的行清掉。
   - `x`：**校验后终止**。只允许 `orphaned`——有属主的进程该由 `s`（写 `stop_requested`）走正常路径。

4. **终止前校验 pid 没被复用**：读 `ps -o lstart= -p <pid>`，与库里的 `started_at` 比对，偏差超过 3 秒就拒绝并说明「pid 可能已被复用」。pid 是会被系统回收的，盲杀可能杀掉一个完全无关的进程。Windows 没有可靠接口，直接拒绝并提示用任务管理器。

5. **两段确认**：`d`/`x` 第一次只把 `confirm` 置成动作字母，第二次才发帧。删除记录与杀进程都不可逆。

6. **先做 TUI，Web 复用同一套 rpc**：新增 `proc.list` / `proc.stop` / `proc.kill` / `proc.clean` 四个契约方法，Web 之后只加页面。

7. **没有 pid 的、从没启动成功的记录**：`pid<=0` 或 `started_at` 为零一律拒绝 `x`，只允许 `d` 清记录。

## 后果

- 属主崩溃后，孤儿从「看不见」变成「能看见、能安全清掉」。
- `x` 的 3 秒容差意味着刚落库的进程在极端时钟漂移下可能被拒；宁可拒绝也不误杀。
- 删记录后 pid/日志仍在磁盘上（输出文件不删），面板不再展示。
- `argv` 只存启动时的前 128 个 token（与命令工具的限制一致），长命令行会被截断。
- 面板按 1 秒无自动刷新；按 `r` 手动刷新，动作完成后自动重拉一次。

## 备选

- **只列当前会话**：看不到已关闭会话的孤儿，等于没解决主要场景。
- **自动杀掉属主失联的进程**：pid 复用会导致误杀；且崩溃后立刻杀可能毁掉用户正想留住的服务。
- **`x` 对 running 也开放**：绕过属主的正常停止路径，跨运行时语义会打架。
- **在 Web 先做**：面板逻辑与服务端契约相同，先 TUI 能更快验证 rpc 设计。

## 修订（v2.55）：Web 端补上同一个面板

TUI 的 `/ps` 落地后，Web 端补了「进程」按钮，走的是同一套 `proc.list` / `proc.stop` / `proc.kill` / `proc.clean`
（`rpc.Core`），没有新增协议与服务端分支。两处差异是刻意的：

- **动作前置确认**：Web 上「终止」与「删除记录」都会弹确认框（浏览器里误点一次没有撤销），TUI 用两段同键确认。
- **动作后重拉两次**（400ms / 1600ms）：属主每秒轮询一次 `stop_requested`，只拉一次很可能还显示「运行中」，
  用户会以为没生效。

同时修掉一个真 bug：本进程主动停止后，`watchStop` 会把 `stopped` 覆盖成 `exited`
（`markStopped` 没写进 `watched`），于是「谁停的」在列表里看不出来。
