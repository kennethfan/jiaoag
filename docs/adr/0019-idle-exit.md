# server 生命周期：按连接数空闲退出

TUI 为了少一步操作会自动拉起本地 `jiaoag-server`。最初的实现让 TUI 在退出时关掉自己拉起的那个进程，于是 server 的生死绑在「谁拉起的」而不是「还有没有人用」：同时开两个 TUI，先退出的那个会把另一个踢下线，而且被踢的那个不会重新拉起。

## 决策

1. **服务端自己决定何时退出。**
   新增 `-exit-when-idle=<duration>`（默认 `0`，即常驻）。开启后，连接数归零时启动倒计时；倒计时结束仍无连接才考虑退出。

2. **有任务在跑就不退。**
   倒计时到点时查一次是否还有活：`running` 视为忙，继续等下一轮；`waiting_approval` 不算忙——审批只能由客户端裁决，没有连接时等下去只会永远不退出。

   `queued` 要分两种（v2.31 修订）：在内存队列里等并发槽的算忙；只剩库里一行 `queued`、内存里没人管的（恢复关着、或恢复重建执行环境失败）不算——它永远不会前进，把它当忙会让服务端在没有客户端的情况下挂过夜。重启时对这类孤立行打 warn。

3. **启动即布防。**
   HTTP 服务起来后如果还没有任何连接，立刻启动倒计时。这样 TUI 拉起 server 后自己崩溃，不会留下一个永远没人用的孤儿进程。

4. **TUI 只负责拉起，不负责关闭。**
   正常退出时不再向子进程发中断，只关闭父进程侧的日志句柄；服务端靠空闲退出收尾。健康检查阶段失败仍然会停掉刚拉起的进程，避免留下半启动实例。

5. **手工启动默认常驻。**
   手工跑 `jiaoag-server` 不带这个 flag，行为与之前一致；需要临时实例时自己加 `-exit-when-idle`。

6. **共用既有的优雅关闭路径。**
   空闲退出与信号退出走同一个关闭流程：关闭所有连接、`Shutdown` HTTP 服务，再由 `main` 关闭应用与存储。不新增关闭协议。

## 后果

- 多开 TUI 互不影响：谁退出都不会影响其他人，最后一个用户离开后服务端在 30 秒内自行消失。
- 任务在跑时会一直活着，即使所有客户端都断开；任务结束后的下一轮检查才退。
- 最多多存活一个倒计时周期，换来「拉起来不用管」的体验。
- 远端部署仍然应该由进程管理器负责，不依赖这个 flag。

## 备选

- **常驻 daemon + 显式停止**：更像正式服务，但对单用户本地工具来说多了一层后台管理。
- **TUI 持有锁文件、最后一个退出者关闭**：需要额外的锁与崩溃清理，收益不如直接按连接数判断。
- **不提供自动拉起**：把复杂度推回给用户，已经被实际使用否定了。
