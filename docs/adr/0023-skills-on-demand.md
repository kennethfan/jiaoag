# ADR-0023：技能包按需加载，索引常驻、正文懒取

日期：2026-11-23
状态：已采纳

## 背景

「技能」（skill）是一份写给模型的操作手册：什么时候用、按什么步骤做、附带哪些脚本与参考文档。社区的形态已经收敛：一个目录一个技能，入口是带 YAML frontmatter 的 `SKILL.md`，`name` 与 `description` 说明身份与适用场景。本机 `~/.agents/skills` 下已经有几十个这样的技能。

jiaoag 原有的两条注入通道都不适合它：

- **项目级提示**（ADR-0012）是每个任务全量注入。技能正文动辄几千字，几十个技能合起来远超上下文预算，而且绝大多数与当前任务无关。
- **`MEMORY.md`**（ADR-0018）同理，它是「项目事实」，不是「可选流程」。

所以需要的是一种**索引常驻、正文按需**的注入方式：模型永远知道有哪些技能、各自解决什么问题，但只有判断用得上时才把正文读进来。

## 决策

- **格式沿用 `SKILL.md`**：`name` / `description` 取自 frontmatter，其余正文原样返回。不发明新格式，直接复用已有的技能库。
- **frontmatter 逐行解析，不用 YAML 解析器**。实测本机 65 个技能里有 3 个的 `description` 含未加引号的 `Triggers: 甲, 乙`，按整份 YAML 解析会直接失败——一条描述丢掉一个技能不可接受。只认 `name` / `description` 两个键，支持 `|` / `>` 块标量，其余行跳过。
- **名字必须可当参数**：不符合 `[A-Za-z0-9][A-Za-z0-9._-]*`（≤64）就退回目录名，避免手写 frontmatter 写坏后在索引里留下乱码。
- **索引进提示，正文不进**：`Catalog.Section()` 生成「名字 + 一句话」的清单，作为 `user:skills` 层追加在内置核心之后（能补充，不能覆盖安全边界）。单条描述截断到 120 字，整段索引上限 10 KB；超出时截断并提示缩小目录。
- **`skill` 工具按需取正文**：`Effects = [read]`，与 `read_file` 同级——不需要审批，也不需要新权限面。返回内容带**绝对基准目录**与一级目录清单，因为技能正文里大量出现 `scripts/x.py` 这类相对引用，不给基准模型只能猜。正文上限 96 KB。
- **路径钉死在技能目录**：模型只能给技能名，给不了任意路径，`skill` 不是第二个 `read_file`。
- **加载失败不阻断任务**：目录不存在、单个技能读不了，都只记日志并跳过；技能是增强，不是运行前提（与 MCP 一致）。
- **目录可配、默认只有机器级**：默认 `~/.agents/skills`；`agent.skills_dirs` 可追加，相对路径按会话工作区根解析。工作区内的技能目录需要显式配置——仓库自带的指令文本属于 prompt 注入面，不该在克隆后自动生效。
- **`agent.skills` 只有 `auto` / `off`**：`off` 既不注入索引也不注册工具。
- **索引进提示词 hash**：技能集合变化会改变 `system_prompt_hash` 与 `extensions_digest`，任务提交时冻结，事后可回答「这一轮能用哪些技能」。

## 后果

- 65 个技能约 10 KB 索引（≈3.4k token）常驻；技能库继续膨胀时要么精简描述、要么拆分目录，边界是显式的。
- 模型需要一次额外往返才能拿到正文；换来的是一次读文件级别的成本，而不是全量注入。
- 技能正文会进 `tool.result` 事件，因此可回放、可审计；代价是长技能会占事件日志体积。
- 技能里如果让模型跑脚本，仍然走 `run_command` 的 argv 白名单与审批，技能本身不扩大执行能力。
- 不支持技能之间的依赖、自动触发、版本管理；这些留给技能库自己解决。

## 备选方案

- **全量注入所有技能正文**：简单，但把上下文预算按技能库大小直接吃掉，且与任务无关的内容会干扰模型。
- **用 YAML 库解析 frontmatter**：格式更严格，但真实技能库里手写文件经常不是合法 YAML，实测会丢技能。
- **把技能做成 MCP server**：能用，但技能本质是文本而不是工具；包一层进程只增加启动成本，还拿不到「索引常驻」的效果。
- **让模型直接 `read_file` 技能目录**：路径依赖模型自己拼，且没有索引，模型不知道有什么可用。
