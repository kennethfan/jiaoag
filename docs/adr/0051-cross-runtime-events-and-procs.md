# ADR-0051：跨运行时的事件与后台进程

- 状态：已采纳（v2.49）
- 日期：2026-11-26

## 背景

ADR-0049 让多个运行时共用同一个库，ADR-0050 让审批可以跨进程裁决。剩下两处仍然是进程内的：

1. **事件广播**：`event.Hub` 只在写事件的进程里生效。A 里跑的任务，在 B 订阅同一会话时看不见——除了 B 从库里回放历史，实时进度是断的。
2. **后台进程**：`exec.ProcTable` 是内存表。A 用 `run_command background=true` 起的 dev server，B 上的 `stop_command` 找不到它；A 崩溃后这些进程变成谁也不认识的孤儿。

另外要明确「谁来收拾死掉的运行时留下的东西」，否则多开几次就会积一堆 `running` 状态的假记录。

## 决策

### 1. 事件：本地 hub + 库里补拉，250ms 一轮

订阅一个会话时同时拿两路：

- 本地 `event.Hub`：本进程写的事件，含 `assistant.delta` 流式块，零延迟。
- 库里按 `seq` 增量补拉：每 250ms 查一次 `events` 表中 `seq > 已发` 的记录，覆盖别的运行时写的部分。

两路按 `seq` 去重：`seq <= 已发` 的直接丢，`seq = 0`（流式 delta）不推进水位。补拉先到、随后本地 hub 又送来同一条时，也会被丢掉。

选择 250ms 而不是「只靠库」或「只靠 hub」：只靠库会丢掉流式体验（delta 从不入库），只靠 hub 则跨进程完全不可见。250ms 是本机 SQLite 上「感觉是实时」与「不必给每次写入加通知」之间的折中。

### 2. 后台进程落 `background_procs` 表，句柄仍归启动它的运行时

表字段：`id / session_id / owner / pid / output_path / started_at / status / stop_requested`。

- 启动进程的运行时是唯一持有 `*os.Process` 的一方，只有它能真正 kill。
- 其它运行时停不了它，只能置 `stop_requested=1`；属主每秒扫一次本地进程表，看到请求就 `Stop()` 并把状态改成 `stopped`。
- 本地进程自然退出后，属主把状态改成 `exited`。
- 表中记录只用于可观测性与跨进程停止请求；内存里的 `ProcTable` 仍是真正的句柄缓存。

### 3. 属主失联的进程标 `orphaned`，不代为 kill

启动时用 `runtimes` 的最后心跳（30s 窗口）判断哪些 owner 已经死了；它们名下的 `running` 进程改成 `orphaned`，界面上只读展示。

不代杀的原因：`pid` 会被复用，按库里的 pid 去杀可能杀掉完全无关的进程。宁可留一个孤儿让人自己处理，也不做这种赌注。

### 4. `-exit-when-idle` 不因「还有别的运行时活着」而推迟

内嵌 TUI 空闲时不会退出，但一个 `jiaoag serve` 没有连接、没有排队/执行中的任务时，按自己的空闲超时退出是正确行为；反过来会让 serve 因为「某个空闲 TUI 还开着」永远不退。别的运行时抢到任务后，任务状态在库里，不会因为 serve 退出而丢。

## 后果

- 跨进程看任务：能看到事件（含阶段与工具结果），但看不到流式 token（delta 不入库）。同一个会话在两个窗口里同时看时，只有执行方的窗口是逐字输出的。
- 事件多了一次每 250ms 的读查询；空闲会话的查询是索引上的空扫，代价可以接受。
- 后台进程的状态以属主为准；属主崩溃后需要人工清理（`kill` 掉进程、记录标 `orphaned`）。
- `stop_command` 在别的运行时上返回「已请求停止」，真正停下有一个轮询间隔（≤1s）。

## 备选方案

- **用 SQLite 的 update hook / 触发器做通知**：需要 CGO 或额外扩展，跨进程也仍要轮询。
- **给 events 表加 `NOTIFY` 式的通知表**：本质上还是轮询，只是多一张表。
- **后台进程的 pid 交给任一运行时代杀**：pid 复用风险，否决。
- **只在 serve 模式下支持后台进程**：会让「内嵌 TUI 也能起 dev server」的能力凭空消失，不必要。
