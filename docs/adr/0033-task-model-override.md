# ADR-0033：单次任务的模型覆盖

- 状态：已采纳（v2.21）
- 日期：2026-11-24
- 相关：ADR-0021（模型列表与会话切换）、ADR-0020（多 key 轮询）

## 背景

`/models`（ADR-0021）解决的是「这一段时间用哪个模型」：它改会话，之后所有任务都跟着变。实际使用里还有另一种需求，粒度更细：

- 用便宜模型做一次大范围检索，再用强模型改代码；
- 复现问题时临时换成另一个供应商的等价模型，跑完立刻回到原设置；
- 脚本化任务（`jiaoag-demo`）想指定模型又不污染会话。

改会话再改回来也能凑合，但有两个问题：中间任何一次提交都用错了模型；改回失败时用户不会察觉，后面全跑在错的模型上。

## 决策

1. `task.submit` 增加 `provider`/`model` 两个可选字段，只作用于这一个任务，空表示跟随会话。
2. App 层新增 `SubmitTaskWith(ctx, sessionID, prompt, SubmitOptions)`；`SubmitTask(...requested)` 保留为只传技能的兼容入口。覆盖体现在传给供应商构造函数的会话副本上，不改库里的会话。
3. 服务端校验 `provider` 存在（拼错直接 `bad_request`），`model` 不做白名单校验：模型列表随时会变，严格校验会让新模型必须先改配置。
4. 覆盖随任务入库：`tasks` 表新增 `provider`/`model` 两列（迁移 0005），`task.queued` 载荷同时带出。重启续跑按任务自己的值重建，不回落会话当前设置——否则用户点名用的便宜模型，重启后悄悄换成贵的。
5. TUI 新增 `/model`：面板选中即绑定「下一条任务」，状态行显示 `· 下一条 <model>`，提交后自动清空。`/models` 仍是会话级切换，两者互不影响。
6. `jiaoag-demo` 新增 `-task-model`/`-task-provider`，便于脚本与冒烟。

## 后果

- 一次任务的模型可以从 `task.queued` 与 `tasks` 表直接回答，审计与回放不需要推断。
- 同一会话的相邻任务可能用不同模型；会话状态行只显示会话默认，单个任务的覆盖需要看任务事件。
- 覆盖不校验模型是否在候选列表内（与 ADR-0021 的取舍一致）：供应商在任务开始时会报错，错误落在任务终态上。
- 模型覆盖不影响系统提示里的 `{{model}}` 之外的内容；提示词指纹因此随覆盖变化，`extensions_digest` 会不同。

## 备选

- **只做客户端**：面板在提交后自动改回会话。省掉协议与迁移，但中间窗口有竞态，且失败时静默跑错模型。
- **在会话上放「下一条任务」字段**：服务端状态更集中，但把一次性意图持久化，队列里多个任务会共用同一个覆盖。
- **允许 `task.submit` 只带 model 不带 provider**：跨供应商模型名不通用，静默拼错比报错更糟；当前实现允许只带 model（沿用会话 provider），但 provider 拼错一定报错。
