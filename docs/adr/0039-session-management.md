# ADR-0039：会话管理（列表、切换、改名、删除）

状态：已采纳（v2.28）

## 背景

会话只能「创建」和「续接」：不带参数启动新建一条，`-c` 接本目录最近一条，`-s ses_x` 精确指定。**没有任何界面能列出会话**——想找上周那条对话，只能 `sqlite3` 查库再手抄 id 给 `-s`。

实测一个用户的库里很快积累到 16 条会话，其中 7 条是 0 任务的空壳（启动 TUI 就建一条，没提交过任务），标题全为空：TUI 建会话时压根没传 `title`。列表既不能看也不能清，这些记录只会越积越多。

服务端其实早就有 `session.list`，但它是给 `-c` 用的「全量更新序」，语义是「挑最近一条」，不是「给我看所有会话和它们的规模」。

## 决策

1. **新增读模型 `session.manage`，不动 `session.list`。** 后者被 `-c` 与 `jiaoag-events` 依赖，扩字段会把「按 `updated_at` 倒序取第一条」的语义带偏。`session.manage` 返回同工作区的会话 + 任务数 + 活动任务数 + token 合计。

2. **工作区由服务端从会话本身取，不信任请求里的路径。** 否则任何客户端都能列举别处的工作；客户端只传 `session_id`。

3. **面板只列当前工作区的会话。** 跨目录切会话会让工作区与实际目录对不上，工具的相对路径全错。要跨项目，重新启动 TUI。

4. **切换是就地切 + 退订旧的。** 新增 `event.unsubscribe`：服务端的订阅按会话 id 分键，不退订就两条流同时往一条连接上推。切换顺序是退订 → 清视图 → `subscribe from_seq=0` 全量回放，两帧在一个命令里顺序写（`Batch` 是并发执行的，并发写同一个 WS 会交错帧）。

5. **有未结束任务时既不能切也不能删。** 审批面板与 `esc` 取消都绑在当前任务上；删掉会话则正在跑的 agent 失去归属，事件无处可写。判定用 `queued`/`running`/`waiting_approval`，由存储层在同一事务里检查（避免「查完再删」的窗口）。

6. **改名只写标题，不复用 `UpdateSession`。** 后者会把 provider/model 一起回写，而改名时手里只有标题，容易把期间切换过的模型覆盖成旧值。改名落 `session.renamed` 事件，回放时标题能回来。

7. **删除是硬删，一个事务里按序清七张表。** 只有 `tasks`/`events` 有 `ON DELETE CASCADE`；`audit`/`approvals`/`proposals`/`tool_calls`/`session_approvals` 不显式删就是孤儿行。顺序：审计（经 `tool_calls` 反查）→ 审批/提案（经 `tasks`）→ 工具调用 → 会话授权 → 任务 → 事件 → 会话。

8. **界面用两次确认，且不提供撤销。** `d` 第一次只提醒并标出「再按 d 删除」，第二次才发请求。删除的记录无法恢复，留回收站只会让人以为可以反悔。

9. **删除当前会话后自动新建一条。** 输入行的 `session_id` 不能指向已删除的会话，否则下一条任务会被服务端拒绝。

10. **只读令牌只能看。** `session.manage` 是读命令，`session.rename`/`session.delete` 归入写命令白名单。

## 后果

- 删会话不撤磁盘改动：它写过的文件还在，`git status` 才是事实。
- 审计的归属依赖 `tool_calls`。`context.compact` 这类没有工具调用的审计本就无法归属到会话，删除后仍留在库里——这是既有的观测缺口，本 ADR 不假装处理。
- 空会话不会被自动清理：删会话连带审计一起删，那是人的决定。
- 名字要手打：没有搜索框。单用户、几十条量级，按时间排序够用。
- 切换会话不换工作区，也不换 `-root` 附加根：那些是启动参数。

## 备选

- **复用 `session.list` 加字段**：会把「给 `-c` 挑最近一条」的语义与「面板要计数」的诉求绑死，任一变化都要改两处调用方。
- **软删（`deleted_at` 列）**：审计能保住，但每个查询都要加过滤条件，漏一处就是「删了还能看见」。真要留档，`jiaoag-events` 已经在做这件事。
- **删除时保留审计**：留下指向不存在会话的行，导出时既不能按会话过滤也不知道属于谁，比删掉更误导。
- **把空会话在启动时自动清理**：自动删数据不可接受，尤其它连带审计。
- **面板内置搜索/标签**：现在没有这个量级的需求，加上去反而要维护一套索引。

## 修订（v2.29）：会话之外也能管理

原决策 2（工作区只从会话本身取）只考虑了 TUI 面板。命令行工具 `jiaoag-sessions` 根本不在任何会话里，按原设计连列表都拉不出来——这是设计漏了使用场景，不是实现缺陷。

修法：`session.manage` 的入参变成三种，按优先级 `session_id` → `all` → `workspace`。

- 带 `session_id`：照旧用会话自己的工作区，行为与决策 2 一致（TUI 面板不受影响）。
- `all`：跨工作区全列，输出多一列工作区。
- `workspace`：命令行显式指定，服务端做绝对化。

放宽的理由：列表只回元数据（标题、任务数、token 合计），不含事件内容与 diff；能拿到令牌的人本来就有权限提交任务、裁决审批。**事件流仍然按会话鉴权**，这一点没有放宽。

同时补上两处工程细节：

1. **路径比对要解析符号链接**。`sessions.workspace` 存的是建会话时给的字符串（`filepath.Clean` 之后），可能是 `/tmp/x`，而命令行给的可能是 `/private/tmp/x`。过滤改成在 Go 里按 `EvalSymlinks` 后的值比较，不再让 SQL 比字符串。
2. **id 支持前缀**。列表显示 12 位短 id，命令行接受任意唯一前缀；命中多条时报错并列出候选，不做静默取第一条。
