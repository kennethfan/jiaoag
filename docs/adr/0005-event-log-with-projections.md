# 事件日志与投影表同事务写入

任务历史需要可回放（断连重连、审计、事后追问「它到底做了什么」），而当前状态需要可查询（会话列表、任务状态、待审批项）。纯事件溯源要每次重建状态，查询与恢复都变重；只存投影表则历史一旦被覆盖就不可追溯。

因此两者都存：`events` 是只追加的事实流，`tasks` / `tool_calls` / `proposals` 等是它的投影；**状态变更与对应事件在同一个事务内写入**，事务外不做迁移。`seq` 为会话内单调递增 int64，由 `sessions.last_seq` 在同事务自增分配，读取方只要求「不重复、不乱序」。

## Considered Options

- **纯事件溯源** — 单一事实来源最干净，但每次查询状态都要回放，且 schema 演进（事件版本）成本高；单用户场景收益不抵复杂度。
- **只存投影表 + 应用日志** — 实现最省，但重连补发、审计、M4 的审批追溯都会缺数据，且日志与状态容易不一致。
- **每个事件单独事务** — 会出现「事件已发、状态未写」的窗口，客户端据此渲染会立刻与库不符。

## Consequences

- 所有写路径必须经 `app`（唯一写者）；绕过它直接写表等于制造不可回放的状态。
- 事件载荷属于线上契约，定义在 `internal/protocol`，服务端与 TUI 共用，不另立一套内部事件类型。
- 流式增量不入库：只持久化 `assistant.start` 与 `assistant.message`，`assistant.delta` 带 seq 但不落盘。**seq 因此允许空洞**，客户端不得假设连续性。
- 事件表只追加、不更新、不删除；清理策略留到 v2（当前不自动清理）。
